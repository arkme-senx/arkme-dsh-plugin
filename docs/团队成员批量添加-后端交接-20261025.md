# 团队成员批量添加：后端交接

日期：2026-10-25。范围：联系人 → 团队 → 团队管理；延续现有团队消息通道、团队内部群规划。

## 目标与当前可验收范围

所有者或管理员在“团队成员”标题右侧点击“＋ 添加成员”，像群聊加人一样从联系人、最近私聊或展开群聊选择多个人，确认后加入团队，默认角色为普通成员。

前端已完成入口、选人面板、搜索、分页、勾选、已选头像、跨来源身份去重、已加入禁选、失败重试和账号切换隔离。备注优先显示。选择普通成员不隐含授予管理员权限。

当前插件没有接通经过验证的团队直接添加接口；这不等同于断言线上服务绝对没有相关能力。已有团队接口是 list-mine、members/list、members/remove、join-by-jotmo-id 和 join-requests 等。群聊的 chats/members/add 绑定群聊，不能用于团队。

本轮“确认添加”只重新检查权限、引用和成员状态，返回 backend_pending；界面明确显示“后端接口开发中，开发完成后此功能完整可用。”并保留选人结果。不会写入团队成员、创建私聊、发送邀请或伪造成功数量。此版本不能作为真正添加成功的验收。

## 已有读取链路

- 联系人：ContactDirectoryService 已有快照分页与备注/头像展示，只在 Host 内转换为真实 user_id。
- 最近对话：SourceService 的 root 分页，仅投影普通私聊和群聊；Bot、团队通道不是候选人。
- 群成员：已有 chats/members/page 和 members/by-user-ids，按需展开读取活跃的真人成员；不改变群成员。
- 已加入状态：当前团队 members/list 所有分页。读取失败不当作“未加入”。
- 前端使用绑定账号与团队的密封 candidateRef；不同来源同一 user_id 投影同一 key，姓名相同的不同账号不会合并。

## 插件内部接口（已实现，非服务端现有协议）

### team.app.member-candidates

入参：expectedAccountKey、teamRef、source（contacts / conversations / group）、可选 sourceRef 和 cursor。

返回：items（key、candidateRef、displayName、nickname、accountName、头像、alreadyMember、isSelf）、groups、hasMore、nextCursor、可选 coverage。

每次重新验证当前团队 owner/admin；cursor 绑定账号、团队和来源。资料/备注仅供当前用户选人，不应同步给被选者或其他成员。

### team.app.members.add

入参：expectedAccountKey、teamRef、candidateRefs（1–50 个不重复引用）、requestUid。

当前只返回 `{ "state": "backend_pending" }`。Host 校验账号、实时团队权限、完整已加入状态、候选引用的账号/团队及一小时有效期，不发上游写请求。

后端可用后，只替换此 Host 边界与结果投影，保留选人界面。接入成功/部分失败回调后刷新真实成员列表、成员总数和团队入口。

## 建议后端协议（待后端确认命名，不能直接当作已上线接口）

建议批量命令：team/members/add，入参 team_id、user_ids、role=member、request_uid。

1. 服务端校验登录态、当前团队成员资格及所有者/管理员权限，不能信任客户端角色。
2. 校验用户真实存在、可加入条件、人数配额、重复用户、已加入状态、团队停用和封禁规则。
3. 对同一团队及操作者的 request_uid 幂等；同键不同目标集合拒绝。网络超时需能查询原请求结果，避免重复执行。
4. 建议逐人结果：added / already_member / invitation_pending / rejected（明确 reason）；返回新的 member_count、membership_revision 与 request_uid。
5. 部分失败只保留失败/待处理的人供用户继续操作；成功的人禁选。不得整批报成功却静默遗漏。
6. 若产品/权限规则要求受邀者确认，则真实返回 invitation_pending，前端显示“邀请已发送”，不能计作已加入。请明确哪些场景支持直接添加、哪些只能邀请。
7. 提供可查询的添加能力 can_add_members、批量上限以及配额/权限原因；客户端当前采用 owner/admin 作为入口候选权限，最终以服务端为准。
8. 成员变化通过现有通知/事件机制同步；通知内容说明加入了哪个团队，由谁发起。加入团队带来的可见范围应明确，不自动扩大个人私聊或私密快记的可见范围。

## 与团队内部群的衔接

如果某群已由后端确认为 roster-bound 的团队内部群，成员增减由后端统一同步，并提供完成/待同步/失败状态。添加团队成员不能由前端再循环调用个人群聊加人接口模拟。尚未关联的普通群不应受影响。

## 后端交付时需要的证据

- 确定的路由、字段、错误码、权限矩阵、直接加入/邀请确认规则与上线环境。
- 成功、已加入、批量部分失败、配额不足、权限撤销、用户不存在、幂等冲突的示例。
- 同一请求网络中断后的结果查询方式。
- 成员列表总数及 revision 更新、实时事件、团队内部群成员同步边界。

## 联调验收

1. 所有者、管理员能操作；普通成员和已退出用户不能绕过入口调用。
2. 联系人和群内同一个人只提交一次；同名不同账号各自保留。
3. 勾选后切来源、搜索、分页、请求失败均保留未成功的选择。
4. 提交前目标已入队或操作者权限变化时，返回真实结果，不重复加入。
5. 多人部分成功、重复点击、超时重试不制造重复成员或重复通知。
6. 跨账号、跨团队、过期引用、伪造引用均失败。
7. 真正加入后成员数、头像、备注、权限和其他设备列表一致。
