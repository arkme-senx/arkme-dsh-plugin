# 手机号绑定冲突处理

## 适用范围

该流程只在以下条件同时成立时启用：

1. 用户正在完成微信扫码登录后的手机号门禁；
2. 当前扫码账号尚未绑定手机号；
3. 插件在发送和校验验证码时显式传入 `resolveConflict: true`；
4. 验证码已经校验成功，且该手机号仍属于另一个账号。

普通手机号登录、已绑定手机号的微信扫码登录，以及未传入 `resolveConflict` 的旧客户端请求继续使用原有链路和返回语义。

## 用户选择

- `login_phone_account`：登录手机号原本绑定的账号，不改变微信绑定关系。
- `transfer_to_current`：经二次确认后，把手机号从原账号原子换绑到当前扫码账号。两个账号及其数据保持独立，原账号不会被删除；后续重新登录时需要绑定其他手机号。已签发 Token 继续沿用现有生命周期，本次不扩展会话撤销能力。

冲突票据和内部用户 ID 由 Host 保存。Browser 只能看到短时、随机且不可反推出后端票据的 `conflictRef`，以及昵称、头像安全引用或默认头像、Arkme ID、注册时间和脱敏手机号；票据、内部用户 ID、验证码和登录令牌不会进入 Browser、Tool 或 SDK 边界。

普通手机号登录不依赖冲突状态机。Backend 使用通用账号变更锁并在锁内复查手机号 owner，登录时间 SQL 也同时校验原 owner；并发换绑时只会登录实时 owner 或返回可重试忙，不会为旧 owner 签发 Token。

## 能力矩阵与威胁决策

| 能力面 | 状态 | 决策 |
| --- | --- | --- |
| 内置 UI | 支持 | 展示脱敏手机号与两个账号的昵称、头像、注册时间、Arkme ID，推荐登录已有手机号账号；换绑必须二次确认并明确影响。 |
| Host API | 支持 | 仅接受同源 DSH Browser 请求；校验操作枚举，只把 Host 内保存的后端票据提交给服务端。 |
| Tool | 不开放 | 验证码输入、账号选择和破坏性换绑需要用户可见的实时确认，模型调用不能替代该确认。 |
| 外部 SDK | 不开放 | 外部插件没有可信的内置确认面，也不应接触冲突票据；因此不注册公开 SDK operation。 |

替代路径是内置 Arkme 登录页。它是本次唯一允许发起账号选择和手机号换绑的交互面。

## 兼容与发布顺序

建议先部署后端，再发布插件：

- 仅部署后端时，旧插件不携带开关，新逻辑完全惰性；
- 新插件连接旧后端时，未知字段不改变正常登录；冲突用户仍得到原有“手机号已绑定”提示，不会误换绑；
- 回滚插件后，后端新增接口没有调用方，旧链路继续工作；
- 故障重试前服务端会重新校验当前账号、手机号归属和票据期限，状态变化时拒绝写入，不猜测用户意图。

上线观察应按结果码和动作记录结构化计数，但不得记录完整手机号、验证码、冲突票据或访问令牌。
