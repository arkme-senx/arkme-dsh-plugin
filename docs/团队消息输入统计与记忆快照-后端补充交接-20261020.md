# 团队消息输入统计与记忆快照：后端补充交接

日期：2026-10-20。接收人：华焱。补充此前《团队消息通道后端协作汇总-20261019》和《团队成员身份与消息详情统一-后端补充交接-20261019》。

## 本轮结果与边界

团队消息输入框已复用普通对话的收件人提示、字数和输入时长组件以及显示开关。收件人优先用查看者的个人备注；团队侧同时注明团队名。聚焦只改变提示可见性，不临时插入一行挤动消息区。草稿开始时间按账号和会话保存到本机，刷新、切换后保留；提交中的请求和随后新写的草稿各有自己的起点；前置拒绝时恢复原草稿起点。

单击正文仍打开阅读侧栏；右键自己已发布的消息 →「消息详情」改用普通对话的 `ArkmeMessageSnapshotDialog`，展示记忆快照。当前能展示正文计算的字数以及 Team 返回的 `created_at`（明确标为创建时间）。发送位置、设备、记录时长、查阅/分享次数等缺失信息显示「未记录」，并说明团队消息相关信息暂未接通。不能把未提供的值当成 0，也不能用当前设备、当前位置补历史。没有自动开启定位或背景录音。

**这不是完整元数据链路已经上线。** 当前草稿计时用于本机输入反馈，尚未随团队发送持久化到云端；后端协议确认后，插件还需补充发送队列、Host 映射和详情读取。此次未改动、部署服务端，也未合并 dev/master。

## 已确认的代码缺口

以插件当前开发分支为准：

- `src/team-send-contract.ts`：`TeamSendInput` 只有会话、幂等 UID、回复序号、正文和文件引用。
- `src/services/team-send-queue.ts`：持久入队与恢复未保存输入开始/完成时间及采集上下文。队列 `createdAtMillis` 是入队时间，不是用户开始编辑时间。
- `src/services/team-app-service.ts`：`team.app.send` 调用 `POST /api/v1/team/conversations/messages/send`；发送体没有完整采集信息。`message()` 投影只取正文、媒体、版本、消息创建时间等字段，没有投影记忆快照字段。
- `src/team-app-contract.ts`：`TeamMessage` 没有记忆快照数据或能力声明。
- `src/services/chat-service.ts`：普通对话的 `source.message-snapshot.detail` 依赖 Chat 会话/记录身份及作者权限，不接收 Team 消息引用。不能把 Team 的 `message_uid` 当成 Chat 的 `record_uid` 调用。

这些证据确认的是**插件及其适配链路缺口**，不能据此认定生产后端完全没有相关字段。请先检查 Team 到 Record 的实际存储、已有详情接口及权限，再决定复用还是补充，避免另建一套记录模型。

## 请后端先确认并提供

1. Team 消息创建时是否生成底层 Record？返回的 `record` 是否存在稳定 Record 身份及作者？消息与 Record 的真实映射是什么？
2. 已有发送接口能否接收普通 Record 同口径的输入时间、设备与位置？字段名、单位、能力版本、最大值和可空语义分别是什么？
3. 是否已有受 Team 会话权限约束的单消息快照读取接口？若有，提供一组脱敏请求/响应；不要求为了插件重新创建路由。
4. `created_at` 的含义与单位是什么？它是服务器创建时间、客户端完成时间，还是原记录时间？不可混用。
5. 能力不支持、该字段历史未记录、被权限隐藏、网络失败，如何明确区分？

下述为建议语义，**不是已经存在的 HTTP 契约**。最终字段名优先复用现有 Record/Chat 模型。

| 数据 | 建议语义 |
| --- | --- |
| 输入开始时间 | 用户开始编辑该条草稿的客户端时间；单纯聚焦不制造历史起点；允许旧客户端缺失 |
| 完成时间 | 用户确认发送这次内容的时间；冻结到幂等发送操作；重试不重新计时 |
| 记录/编辑时长 | 明确是自然经过时长还是活跃输入时长；本次前端沿用普通对话自然经过时长，不是音频时长 |
| 创建时间 | 服务端当前 `created_at` 的真实含义，单独保留 |
| 同步时间 | 服务端最终持久接收的时间；不能取页面打开或客户端重试时间 |
| 采集上下文 | 当次记录的终端名称/平台、网络类型、电量及充电状态，并带采集时点；不要包含凭据、IP、SSID 或硬件序列号等无必要数据 |
| 位置 | 用户已开启且授权的当次位置、精度、采集时点；无权限、未开启、不可用与未采集分开 |
| 其他快照字段 | 天气、海拔、移动状态、归属日期等已有则复用，未提供留空 |
| 查阅/分享次数 | 只提供已有且口径明确的计数；不能用团队已读人数代替查阅次数 |
| 背景音 | 本期不额外开启采集；若后续支持必须沿用独立权限、状态和播放授权 |

## 发送与读取闭环要求

### 发送持久化

- 可选元数据与 `client_message_uid` 绑定，贯穿入队、落盘、上传附件、重启恢复、提交、状态查询与发送成功投影。
- 同一幂等 UID 的正文及完成时点冻结；网络超时后先核对，不生成第二条消息或另一份采集历史。
- 拒绝前未被接受的请求允许回到原草稿；已接受/结果未知的请求继续沿原 UID 恢复。下一条草稿不能继承上一条的开始时间。
- 重编辑形成独立编辑上下文和编辑时长，不覆盖首次记录上下文；原始创建/完成时间保留。
- 服务端校验时间范围、单位、设备字段长度及结构。客户端时钟不可信，不能作为权限判断或服务端同步时间。
- 旧客户端省略新字段仍能发送；新客户端不能因为没有快照能力就发送失败，也不能伪称已经保存。

### 详情读取与权限

- 读取时验证当前账号、团队会话、消息可见侧、作者、当前成员资格和消息状态；旧引用不得绕过撤权。
- UI 本期仅对自己消息开放记忆快照；**作者设备和位置不是团队公共已读信息**，不能因同属团队就返回其他人的设备/位置。
- 如通过底层 Record 读取，映射必须由服务端校验，不能接受前端任意拼的用户 ID/Record UID。
- 返回字段状态及能力版本。历史缺失显示未记录；临时读取失败可重试；不支持明确说明；0 电量或 0 时长是有效值，与缺失不同。
- 消息删除、账号切换、成员退出或权限撤销后，快照和缓存均不得继续泄露正文或敏感元数据。

## 插件收到协议后待补充

1. 为 Team 内部操作添加受保护的快照读取入口及完整投影，继续复用当前弹窗；不要暴露原始内部 ID 给界面。
2. 按既有采集权限，在提交时冻结上下文；将输入开始、完成、时长等随发送任务落盘，补全重启/重试测试。
3. 有能力声明后才送新字段；使用响应中的真实数据替换「暂未接通」提示。
4. 元数据异步补全不刷新整条消息正文、不抢焦点、不影响阅读滚动。

## 验收用例

- 普通文字、仅附件、粘贴图片、重新编辑；只有实际输入开始计时；清空全部内容后新草稿重新计时。
- 两个团队会话及两个账号交替编辑：草稿、计时、备注互不串用；刷新后恢复各自起点。
- 网络超时、服务拒绝、重启恢复：幂等消息唯一，首次完成时点不漂移，新草稿不被覆盖。
- 发送成功后右键自己消息打开快照；关窗/重进/跨端读取一致；单击正文仍是阅读侧栏。
- 历史缺字段、真实 0 值、服务未支持、读取失败分别验证；不能显示当前设备作为历史设备。
- 自己消息、他人消息、外部访客、退出团队、撤权、消息删除分别校验；他人设备/位置不可被枚举。
- 确认创建时间、开始时间、完成时间、同步时间含义和单位；客户端时钟偏差不扰乱服务端事实。

前端已有回归覆盖草稿起点持久化、失败恢复、共享显示开关、右键快照与单击阅读的分离，以及缺失快照字段不冒充 0。真实元数据闭环仍待服务契约与联合验证。
