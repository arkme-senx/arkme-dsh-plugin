# 录音实体相关性与反馈一期后端交接

日期：2026-10-15。前端仓库：arkme-dsh-plugin。开发分支：`codex/ts1015-02-实体相关性与反馈`，基于 dev `283a0548`。本次不修改、部署后端，不合并 dev。

目标是让全天录音中的实体优先反映用户本人及与其直接交流的内容，减少手机播放、远处人声等噪声；同时区分“与我有关”和“名称识别正确”。前端已经接入下面的待实现协议。本文不是生产能力已上线的声明，示例数据均为协议示例，不需要用户提供个人 candidates JSON。

## 前端行为

保留现有实体入口图标、侧栏、分类、提及分页、原文定位与高亮；转写工具栏仍位于文本框内右上角。

```text
实体 · 数量                         关闭
[与你相关] [全部]
[全部] [人物] [组织] [地点] ...

实体名称                      N 次提及
类型 · 你提到 / 与你交流时提到 / 你关注的
  时间 · 声音来源 · 待核实（如有）
  原文片段（点击定位）
  反馈 → [与我有关] [播放内容] [识别有误]
         仅影响这次提及，保存后可撤销。

其他内容 · N（可展开）
```

- 有 v1 相关性信息时默认“与你相关”，本人提及优先，其次用户明确关注、直接交流；其他与未知来源可展开，也可切换“全部”。分类筛选与相关性筛选叠加。
- 同一实体可同时出现在本人发言和视频里。实体层是聚合排序，提及层始终显示自己的来源；不能把其中一次的来源套给整个人物/实体。
- 无 v1 信息时默认全部，禁用“与你相关”，显示“暂未提供相关性信息，当前显示全部实体。”不把已知昵称当相关性证据，不凭空把播放声认作本人。
- 未开放写入或原文版本无法精确匹配时，反馈菜单只展示禁用项和不可保存说明。
- 保存不乐观修改数据；服务端确认后才显示成功并刷新。失败/超时不自动重放；重试沿用同一个操作编号。撤销只针对最近一次成功操作的回执。
- 账号/日期切换取消当前请求，忽略晚到响应。未知结果重试仅保留在当前页面实例内；刷新浏览器后不会自动补发旧写入，应以服务端读回事实为准。

## 来源与相关性如何判断

来源、相关性、识别准确性是三个独立维度。

| 字段 | 值 | 含义 |
| --- | --- | --- |
| relevance | self | 有可信依据为用户本人现场提及 |
| relevance | conversation | 有可信依据处于与用户的直接交流，不是仅仅认识该声音 |
| relevance | concerned | 用户明确反馈“与我有关”，允许来源为 playback |
| relevance | other | 其他提及 |
| relevance | background | 背景、播放等未建立用户相关性的提及 |
| relevance | unknown | 无足够证据，不能默认 self/conversation |
| sound_source | unknown / in_person / playback | 未知、现场声音、设备播放 |
| accuracy | unverified / needs_confirmation / confirmed | 未核实、存在疑点、已按明确证据核实 |

人工说话人标记只说明身份，不足以证明是在与用户交流。结合本人参与的轮次、对话时段、时间邻近、来源纠错等做判断；证据不足返回 unknown。历史“周鹏”簇可能混入手机播放声，不能直接把该簇全部设为 conversation。

人工事实优先于自动判断；不得在任务重跑时清掉用户反馈。接入 `docs/录音说话人纠错一期-后端交接-20261014.md` 中来源事实时，以有版本的具体音频片段为锚点。实体反馈“播放内容”只影响该次提及的来源判断，不直接改声纹库、人物绑定或整个说话人分组；后续扩大到片段/附近声音需要另行明确范围。

实体聚合建议：有 self 提及则 self；否则有 concerned 则 concerned；否则有 conversation 则 conversation；只有明确背景提及才 background；剩余按 other/unknown。计数继续表示所有提及，不能只计筛选命中的次数却仍用旧 total。准确性采用保守聚合：存在未解决疑点显示 needs_confirmation，不把某次确认扩展为其他同名提及都正确。

## Relation 读取接口增量

沿用已有 POST 路由、当前用户鉴权和 `{ "code": 200, "data": ... }` 封装。下面示例展示 data 或请求增量。不能由客户端指定其他用户作为 owner。

### audio day list

`POST /api/v1/entity/audio-day/list` 请求新增可选 `known_personalization_revision`，现有 day_stamp、transcript_source、active_transcript_source、known_state_revision、known_projection_revision 保持原义。

响应新增：

```json
{
  "personalization": { "contract_version": 1, "revision": 4, "feedback_supported": true },
  "entities": [{
    "entity_key": "existing-stable-key",
    "official_entity_id": "existing-entity-id",
    "canonical_name": "示例项目",
    "type": 6,
    "occurrence_count": 3,
    "relevance": "self",
    "accuracy": "unverified"
  }]
}
```

- 示例省略已有任务字段，实际必须保留原协议必需字段；provisional 仍使用 projection_entity_id。
- 缺少 personalization 或不支持的 contract_version，前端安全回退全部列表，不使用其相关性/反馈字段。
- v1 revision 为非负安全整数；feedback_supported 必须为布尔值。实体 relevance/accuracy 可省略，按未知/未核实展示；出现时必须为上述枚举。
- revision 覆盖当前用户、日期、转写来源的相关性、来源、准确性、反馈状态及写入能力；这些内容变动必须增加 revision。其他账号的偏好不能串入。
- **增量读关键点**：known_personalization_revision 缺失或不匹配时，即使 projection_revision 未变化，也必须返回完整实体列表。仅当结果身份与个人信息版本都一致，才能省略 entities。空数组明确清空，省略表示不变。
- Host 将 revision 纳入实体 version 和密封引用；否则反馈后旧提及缓存会继续显示。不要只增加 state_revision。

### audio day occurrences

`POST /api/v1/entity/audio-day/occurrences` 请求保留原协议。响应顶层返回与 list 同一版本的 personalization；每条 occurrence 可新增：

```json
{
  "occurrence_id": "existing-stable-mention",
  "feedback_version": "mention-feedback-version-8",
  "context": {
    "relevance": "concerned",
    "sound_source": "playback",
    "speaker_label": "可选的当前用户备注名",
    "accuracy": "needs_confirmation"
  }
}
```

其余 row_id、session_id、child_id、item_index、transcript_source、rune_start、rune_end、observed_text、start_ms、end_ms 原样保留。

- context 可省略；存在时 relevance、sound_source、accuracy 必填；speaker_label 可选且不超过 200 字符。备注优先；没有可靠身份不编造昵称。
- feedback_version 是非空并发校验令牌，绑定这次提及及其原始证据/来源版本。该次提及的事实或原文变化后必须失效。
- Host 校验真实转写、Unicode 位置、原文片段与当前结果版本后，才发给浏览器密封 feedbackRef。没有精确原文或没有 feedback_version 不允许反馈。
- list 与 occurrences 的 personalization revision 不一致会拒绝旧引用并要求刷新。声音来源可与 related 状态独立，例如示例中的“用户关注的播放内容”。

## 反馈写入和撤销

### POST /api/v1/entity/audio-day/feedback

```json
{
  "job_id": "existing-job",
  "view_mode": "official",
  "projection_revision": 14,
  "result_version": "existing-result-version",
  "occurrence_id": "existing-stable-mention",
  "expected_feedback_version": "mention-feedback-version-8",
  "expected_personalization_revision": 4,
  "action": "playback",
  "scope": "occurrence",
  "idempotency_key": "client-generated-uuid"
}
```

provisional 时 result_version 为空字符串，使用 projection_revision；official 使用 result_version。服务端验证当前用户可访问该任务与提及，并检查完整版本、来源、原文证据、能力开关。scope 只接受 occurrence，不允许默默扩到全部同名实体、当天、说话人簇或人物。

| action | 保存效果 | 保持不变 |
| --- | --- | --- |
| relevant | 此提及增加用户关注事实，聚合显示 concerned（如果已有可信 self 则保留 self） | 原来源、声音身份与准确性 |
| playback | 此提及来源设为 playback；没有人工关注事实时降低为背景相关性；原 self/conversation 的现场推断失效 | 识别文本、人物身份；已有人工关注事实 |
| incorrect | 此提及增加待核实事实，accuracy=needs_confirmation | 保留原名、证据、来源，不猜一个替代名称，不删除实体 |

成功响应：

```json
{ "status": "applied", "receipt_id": "opaque-owner-receipt", "undo_expires_at": 1792022400000 }
```

undo_expires_at 为毫秒时间戳，例值仅表示格式，实际由服务端产生。成功必须意味着事实和回执均已持久化，后续 list/occurrences 可读回新版本。不要返回 accepted 后让前端误认为已经保存。

确定未执行时，可返回 HTTP 200 / code 200 的 `{"status":"rejected","reason":"stale"}`，reason 可为 stale/unsupported/forbidden/undo_expired/conflict。前端会刷新并解除本次操作锁。非 2xx、超时、无效回执均按未知结果处理，不声称保存失败或成功，保留相同请求编号重试。

### POST /api/v1/entity/audio-day/feedback/undo

```json
{ "receipt_id": "opaque-owner-receipt", "idempotency_key": "another-client-generated-uuid" }
```

成功 `{"status":"undone"}`，确定未执行仍用 rejected。回执必须绑定当前用户、原提及、操作、原版本、过期时间；使用可撤销事实或条件补偿，不能用旧快照覆盖后来其他端的修改。有冲突明确拒绝，读回当前事实。

### 幂等和并发必须满足

1. 接口按当前用户 + 操作类型 + idempotency_key 保存请求指纹和结果。相同编号不同内容拒绝；相同内容返回原回执。
2. **先查幂等回执，再查当前版本。** 首次已提交但响应丢失时，客户端携旧版本重试必须读回首次回执，不能误报 stale 或重复写入。
3. 并发检查和事实更新、revision 递增、回执写入应原子执行。不可部分保存后返回 rejected。
4. 撤销也遵守幂等，已成功撤销后的同编号重试返回原结果；未知结果重试即使超过 UI 撤销时限，也先恢复已存在回执。
5. Host 不在重试前重新查询当前版本以免截断幂等恢复；以上鉴权/版本检查最终由后端负责。浏览器只持密封引用，不接收原始任务/片段/回执 ID。
6. 建议只有所有写入、读回、撤销验收通过后才开启 feedback_supported；读取相关性可先单独上线。

## 第二期音频复核建议

本期没有接入新 ASR 或音频模型，不宣称降低了真实名称识别错误率。建议后续让后端以原音频和可追溯证据复核疑点：

1. 保存原始 ASR 文本、候选名、原音频精确时间段和原文版本，不覆盖原始证据。
2. 优先处理与用户相关且名称有疑点的片段；按音频片段去重，截取必要上下文，限制成本与任务时长。
3. 结合音频二次识别、原 ASR 候选、用户通讯录/项目词表、上下文核对；词表仅作候选，不把所有近音词强行改为熟人/已知品牌。
4. 有差异保留“原转写 → 建议名称 → 证据来源”，低把握维持待核实；用户可以试听、确认或否定。另一个模型与原模型同意也不是独立正确性证明。
5. 原文定位始终锚定原始转写版本与范围；名称归一化不能把高亮偏移改错。用户确认应有版本、审计和撤销，不能影响其他同名对象。

音频复核的路由、模型、成本、置信度校准和用户确认界面需要独立设计，未包含在本期写接口中。

## 联调验收

| 场景 | 必须结果 |
| --- | --- |
| 旧后端 / 未知 contract_version | 全部真实实体可查看，相关性禁用，无虚假保存 |
| 本人、直接交流、背景、未知混合 | 本人优先；相关性与类型共同筛选；其他可展开 |
| 同一实体同时出现在现场与视频 | 每条提及独立来源，不整实体改成播放 |
| 用户关注一段播放内容 | 显示在相关视图，同时仍显示播放内容 |
| 识别有误 | 标记待核实；不自动改名、删原文或删除实体 |
| 无精确原文 / 缺少反馈版本 | 可以查看，不能发反馈写入 |
| 反馈确认后刷新 / 跨设备读取 | 事实持久化，列表与提及版本一致，原文定位正常 |
| 丢失成功响应再重试 | 相同幂等编号，恢复首次回执，仅一次实际写入 |
| 同编号不同请求 / 跨账号引用 | 拒绝，不泄露其他用户数据 |
| 并发修改、任务重跑、切换转写源 | 无旧版本覆盖；人工事实不会被重跑删除 |
| 撤销后刷新 / 撤销响应丢失重试 | 事实读回正确，幂等一次，不覆盖后来修改 |
| capability 开关变化 / 只变个人信息版本 | 版本递增，返回完整实体；不能残留旧 refs |

前端自动化覆盖点：旧协议回退、筛选/展开与定位、来源与准确性独立、保存确认、撤销、超时同编号重试、账号/日期切换、密封引用范围、原文失效禁止反馈、Host 写入 Origin 校验。生产联调需后端提供包含上述字段的真实结果，再完成“保存→刷新→撤销→刷新”验收。
