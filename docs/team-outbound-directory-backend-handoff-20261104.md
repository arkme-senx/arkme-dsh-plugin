# 团队主动联系：零消息会话的目录可见性后端交接

本文保留交接时的历史状态。当前实现合同见 [明确团队联系与零消息目录](team-member-contact-directory.md)，验收及上线状态另列。

用户确认：从群成员或联系人名片选择团队并成功发起后，该用户应立即出现在自己的团队会话列表；会话列表的存在与发送首条消息独立。刷新、重启和跨端仍应能找到已主动发起的会话。

## 已确认的当前合同

- `jotmo-team/internal/teammessaging/reception.go` 的 `OpenByMember` 校验团队成员、接收通道、目标账号及屏蔽状态后返回零消息关系，未发送消息。
- `internal/teammessaging/repository.go` 的 `MongoStore.Conversations` 使用 `last_seq > 0` 过滤，团队与访客两侧均排除零消息关系。
- `service.go:List` 依赖上述查询；普通团队入口恢复和公开链接读取也刻意不激活零消息会话。不能把所有浏览、公开链接预览或云端置顶产生的空关系直接放入列表。

## 需要 Team owner 补齐

1. 持久记录经过完整权限校验的成员主动联系意图，将它与被动打开/预览空关系区分。使用 `open-by-member` 的权威事实；不能信任客户端声明的访客身份或私造消息序号。
2. 团队侧列表纳入本次授权成员主动发起的关系，包括尚无消息的会话。明确其团队内共享范围；访客侧的列表、通知和未读仍按实际消息与既有规则处理。
3. 该状态不生成首条消息，不增加 `last_seq`、未读、阅读回执或发送通知。首条真实消息到达后按同一 conversation UID 合并，保持幂等。
4. 明确排序时间、游标和索引。当前活动索引是 `last_seq > 0` 的 partial index；新查询与索引必须配套，不以扫描全部空关系代替分页。并发主动发起、发送及取消不能使跨页重复/漏项或顺序反复变化。
5. 保持团队成员/账号状态、暂停通道、屏蔽与接收资格的权威检查。离队或失去权限后不可继续列出旧关系，跨账号、跨团队不可混入。
6. 明确旧客户端、滚动发布和回退行为；新增状态可兼容缺失字段，未主动发起的历史空关系不批量激活。已有移除/恢复和置顶偏好继续按各自事实判断，不靠消息序号伪装活动。

## 建议验收

- 隔离真实 MongoDB + Team HTTP：主动联系后不发送消息，团队列表、分页、刷新/重新登录及另一授权端可看到相同会话；外部用户无新增消息、通知和未读。
- 同一目标重复打开、并发打开与首条发送、发送失败/取消、事务回滚、成员资格/通道/目标状态变化、已移除后主动重开、跨账号和大用户标识。
- 对并发路径执行 race 检查，比较旧/新查询执行计划、扫描行数和请求放大；按仓库规范复核鉴权、合同、快照/分页、滚动兼容及回退。

## 前端适配边界

前端先将 Host 成功确认的会话加入当前账号的共享目录，两个主动联系入口共用处理；普通列表缺少零消息项时保留当前会话，不让异步旧响应覆盖新行。零消息预览显示「尚未发送消息」，未读数不伪造；首次真实消息按稳定标识合并。

该展示补齐不代替后端持久事实。浏览器/Provider 重启及跨端恢复仍依赖本交接落地。后端代码保持未修改，本文件供 Team owner 实施与审查；未通过消息工具发送给任何人。
