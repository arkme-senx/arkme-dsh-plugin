# 团队入群与发言身份：后端交接

日期：2026-10-25。承接 [双向团队私信](./双向团队私信-后端交接-20261025.md)。团队全员自动加入的内部群是另一种关系，见 [团队内部群与成员自动同步](./团队内部群与成员自动同步-后端交接-20261025.md)。

## 1. 目标与阶段

1. 双向团队私信：用户可联系团队，团队获授权成员也可主动联系用户；同一团队和用户复用同一会话。
2. 本阶段：团队作为独立成员加入群聊；授权成员从团队工作区查看、回复；个人和团队身份明确区分。
3. 下一阶段：群内用户与团队的互动以原消息引用归集到对应团队私信。不是复制消息或自动把私信发回群。

团队“成员资格”、个人“群成员资格”、团队“群成员资格”、本人“团队代理权限”是四件不同的事情，不得相互替代。

## 2. 当前仓库实现与限制（请先阅读）

已落地的是可操作的入口和明确的待接入状态：

- 群成员 → 添加成员：联系人、Bot、团队三个分类。团队分类读取本人实际所属团队，用户选中后可发起检查。
- 团队消息第二栏：复用原总入口，只有一个列表，没有用户／群聊分类。保留置顶、未读、最新消息排序、分页和滚动位置。当前真实数据仍只有团队私信，团队群待后端提供；不将个人群聊插入充数，也不展示虚构群卡片。
- 输入框只在服务端明确返回至少两个有效发送身份时提供选择器；普通群、团队内部群、仅一种身份、资格未知或接口开发中均不显示。目前 Host 未提供 ready 资格，因此真实普通群不显示，也不为此额外请求。原紧凑角色菜单已保留为待接入组件：本人头像＋“我”，候选保留本人头像与团队角标；现阶段不会真正切换团队发送。
- 不调用个人加群、Bot 加群、个人私信或普通发送接口模拟团队行为，不生成本地假团队成员、假群聊或假消息。
- 当前不轮询这些新能力：入群页挂载、打开身份菜单时按需读取，失败可重试。团队群列表 pending Host 边界保留，但前端不再单独请求、展示一个群聊分类页。
- 本阶段没有实现真正的团队入群、团队群消息读取／发送、身份切换后的草稿隔离、群消息聚合或团队代理群窗口。上述功能需要后端权限和消息语义后再对接并联调。

现有代码证据：

- `src/services/group-service.ts`：`members/add` 使用个人 `target_user_id`，Bot 走独立接口。
- `src/team-app-contract.ts`：现有 TeamConversation 是团队与外部用户的一对一会话。
- `src/client/ArkmeSelfRolePicker.tsx`：自定义角色是个人快记的显示角色，不是团队授权凭证。

## 3. 已实现的插件 Host 边界（不是已部署的云端接口）

类型在 `src/team-group-contract.ts`。三项均携带 `expectedAccountKey`，Host 在操作前后核对账号，不能跨账号复用引用。

| 操作 | 请求 | 当前返回与校验 |
| --- | --- | --- |
| `team.app.group.context` | `sourceRef` | 解开当前账号的群引用，确认 group_chat，读取 list-mine；返回 `{state:'backend_pending',teams:ArkmeTeam[]}` |
| `team.app.group.join` | `sourceRef,teamRef,requestUid` | 验证群引用及当前团队成员资格；返回 `{state:'backend_pending'}`，没有入群写入 |
| `team.app.group.directory` | `teamRef` | 验证账号及当前团队成员资格；返回 `{state:'backend_pending'}`，不读取个人群当作团队群 |

`list-mine` 只用于展示真实所属团队，不能证明该团队已在群内、本人可代表该团队发送、或本人有权限邀请团队。当前 pending 校验也不代表入群资格审查已通过。

`sourceRef` 和 `teamRef` 分别由不同服务签发，必须通过各自 codec 解开，禁止把客户端传来的名称、team id 或 user id 当作授权。

统一提示：“后端接口开发中，开发完成后此功能完整可用。”前端会拒绝未知返回状态，不把缺字段的结果按成功处理。后端接通时需同时升级 Host 映射和前端 ready 分支，不能只修改状态字符串。

## 4. 产品约定

### 4.1 入群与可见范围

- 团队是一个群成员主体，不是批量加入其所有员工。
- 加入同时满足群的邀请／审批规则与团队的入群授权；双方权限均由服务端判断。
- 群中出现明确系统通知：某团队已加入，获授权的团队成员可查看、参与群聊。
- 默认可见范围从团队加入时的消息序号开始。个人早期群历史、个人私信均不因团队入群而转为共享内容。
- 团队内部授权成员无需个人入群，也能从团队工作区读取授权范围内的群消息。
- 团队退出或被移除后立即停止新的读取和发送；重新加入生成新的成员版本和可见边界，不能复用旧凭证绕过限制。
- 本阶段默认撤销权限后不再开放历史在线查询；如业务要求离职／退群后保留审计，请另行定义审计权限，不能沿用普通成员读取权限。

### 4.2 输入身份与草稿（后端 ready 后联调）

- 团队内部群绑定的是人员名单，统一以本人身份发言，不出现身份选择。普通群只有个人身份也不出现选择器。
- 团队作为主体加入的普通群，只有个人群资格与团队代理资格同时有效（或确有多个团队身份）才出现选择器。只可代理一个团队时固定团队身份，在原有发送提示显示对应团队，无下拉。
- 不得从 list-mine、群名、当前成员恰好都是同事推断绑定关系或团队代理权限。

- “团队身份”是本人代表团队发言，不是匿名团队账号。选择菜单始终保留本人头像；默认简写“我”，团队候选显示“我 · 某团队”和“代表团队发言”。
- 团队模式下，收起的入口仍为本人头像＋团队角标＋“我”；悬浮提示完整团队名称。在输入框已有的发送提示位置展示“以「某团队」身份发到「某群」”，不新增永久说明行、不把长团队名塞入按钮。
- 普通群入口默认个人；团队工作区入口默认所代表团队。用户明确选择后，在本机当前账号、群、入口上下文内记住选择。
- 只展示当前有资格的两类身份：个人和团队。用户不属于该群时不开放个人发送；多个可代理团队逐一列出名称与标识。
- 个人快记的自定义角色不能出现在群身份候选中；不新增角色管理入口。
- 回复、被 @、刷新消息和后台权限更新不得悄悄更换发言身份。
- 每种身份分别保存草稿（文字、附件、引用、输入统计、上传状态）；切换后恢复该身份的草稿，而非将个人草稿改用团队身份发送。
- 发送开始冻结实际操作者、代表身份、群、附件和引用。权限变更时拒绝发送并保留原草稿，绝不能降级为个人发送。
- 快捷键发送、表情、语音、长文、转发、详情延展以及离线重试都必须走相同身份校验，不能只修主发送按钮。
- “发给自己”即使未来使用团队身份标签，仍是本人私密内容；不因此赋予团队读权限。

### 4.3 群中的展示

- 所有人（包括发送人、同事和外部群成员）都能直接看到实际操作者与代表团队，不能只在详情中披露操作者，也不能仅用团队头像、名称替代本人。
- 消息主头像使用实际操作者头像，叠加团队角标；名称行显示“发送人名称 [团队名称]”。昵称和头像走正常用户展示路径，名称优先使用当前查看者的联系人备注。点击头像仍是实际发送人的个人卡片。
- 详情中进一步明确“由某成员代表某团队发送”。头像缺失使用个人头像占位，不改用团队头像冒充本人；原消息的代表团队和操作者身份不可因后来退群或改身份而改变。
- 只有实际本人发送的消息使用本人消息底色，同团队其他成员消息不冒充自己的消息。
- 原群成员列表中团队占一个位置，不能把员工账号伪装为团队账号或 Bot。
- @团队使用团队成员引用；接收提醒的是有权限的团队成员。提醒、未读和消息计数都以原消息唯一键去重。

### 4.4 团队混合会话列表

- 团队总入口打开后，团队私信与团队群聊混排，不分 tab、分组或两个列表。保持联系人 → 团队与第二栏总入口共用同一界面。
- 置顶优先，同一区域按最新消息时间降序，同时间用稳定会话键排序；不能由群资料编辑、已读回执或分页返回时间把旧会话顶上来。
- 群卡片显示群头像、群名、最新发言人及预览；私信卡片显示外部用户头像、名称和预览。沿用普通第二栏未读、选中、右键与窄屏呈现。
- 后端优先提供按权限过滤、统一排序分页的混合列表，携带 `conversation_kind: team_direct | team_group | team_internal`、稳定会话键、最新消息时间、预览、未读、代表团队及签名会话引用。
- 如果两个来源仍分别分页，Host 必须维护两边游标并合并到同一个有序分页结果；不能先加载全部私信再附加群聊，或因为第一页暂时没有群而认定没有团队群。未读与私信／群原消息引用按唯一键去重。
- 团队群的打开、预览、置顶、移除、恢复及刷新采用对应代理会话语义，禁止将团队群引用交给现有仅支持一对一的 `team.app.timeline` 等接口。移除只隐藏入口，不退出群。
- 接口部分失败保留已加载列表，明确受影响的数据范围并支持重试；无权限时剔除相应群，不伪装成功或空列表。后台刷新保留正在阅读的会话与滚动位置。

### 4.5 后续群内互动归集

- 归集显式 @团队、回复团队消息、团队对指定用户的群内回复，进入 `(team, external_user)` 对应通道的“来源群聊”引用卡片。
- 与团队无关的普通群消息、员工个人身份的历史交流、个人私信不自动归集。
- 同一条消息只存一份业务事实。群视图和团队私信视图通过引用呈现同一来源，不重复发送、计未读或通知。
- 在来源卡片上回复，默认回复原群，输入前明确“回复到某群”。转入团队私信必须用户明确选择，禁止混淆公开与私密目的地。
- 查看原文、展开上下文、复制链接、转发都重新检查来源群权限。外部用户不能通过团队私信获取其无权访问的群消息。
- 编辑／撤回／删除在引用视图反映同一版本；不保留可绕过原权限的完整消息副本。

## 5. 后端所需能力（建议协议，路径待后端确定）

请先确认语义与字段再定 HTTP 路径，以下不是客户端正在调用的上游接口。

| 能力 | 关键请求 | 返回要求 |
| --- | --- | --- |
| 当前群的团队候选与发言上下文 | group uid | 个人是否为群成员、各团队成员状态、是否可邀请／代理发言、拒绝原因、权限版本 |
| 团队申请／加入群聊 | group uid、team id、request uid、预期权限版本 | joined / pending_approval / rejected / already_joined；成员引用、版本、可见起始 seq；同一次请求幂等 |
| 团队混合会话列表 | team id、cursor、limit | 按授权过滤的私信与群聊，类型、稳定会话键、最新消息时间、预览、未读和统一排序分页游标；不可用、无权限和空列表分开 |
| 团队代理群会话上下文／时间线 | team group membership ref、cursor | 校验代理权限；原群消息身份与 seq；不能返回加入前越权内容 |
| 以团队身份发送与状态查询 | group ref、team ref、message request uid、权限版本、内容／附件／引用 | 原消息唯一 id、版本、实际操作者、代表团队、幂等结果；明确最终拒绝与未知结果 |
| 权限／成员变化推送 | 团队及群订阅 | 入群审批、移除、离开团队、权限收回、账号切换后停止消费；触发上下文重读 |
| 团队身份消息读取／已读 | group ref、team context、seq | 明确个人阅读事实及团队工作区聚合，避免双入口重复计数 |
| @团队与来源引用归集 | 原 group/message/team/user 引用 | 下一阶段；保留来源权限、目的地和去重键 |

推荐群成员模型新增 `principal_kind: user | bot | team`，团队成员记录使用 team id，个人操作者始终来自认证态，不能相信客户端提交的 actor id。

推荐消息在原来的实际发送者字段外增加：

```text
represented_principal_kind: personal | team
represented_team_id: optional
actual_actor_user_id: server assigned
actual_actor: viewer-scoped nickname / public_nickname / avatar_ref / person_ref / is_me
represented_team: id / name / avatar_ref
team_group_membership_uid / membership_revision
origin_group_uid / origin_message_uid / message_revision
```

上面是建议语义；插件浏览器端仅接收必要展示字段和签名引用。操作者的公开头像、名称与团队名称需向所有有权读消息的群成员返回，不得只向内部成员返回。联系人备注按查看者解析，不能把某人的私人备注发给所有人。大整数 id 沿用现有字符串／owner codec，不能 JavaScript Number 化。

本地发送队列和云端幂等键必须包含发送身份／上下文。相同 request uid 但身份或内容改变应返回冲突，不允许“重试”变成另一个身份的新消息。

## 6. 联调顺序

1. 与前一份文档的双向团队私信协议统一 team/user 会话唯一性、实际操作者和代理身份。
2. 团队入群、权限上下文、列表、代理时间线和发送形成一个可用闭环，再开放身份切换。
3. 前端接入 ready 分支、草稿隔离、所有发送入口、成员展示、读状态及推送撤权；跨设备核验。
4. 再做 @团队和群内互动归集。普通群与团队视图保持同一消息事实和权限边界。

## 7. 验收清单

- 本人同时有个人群成员资格和团队代理发言资格时，两种身份可选、草稿互不混用；收起按钮紧凑，现有发送提示明确团队；本人、同事、外部用户都能在消息上直接识别操作者和团队。
- 私信和群消息交替到达时同一列表正确重排，置顶优先；跨来源分页、同时间排序、列表部分失败、重进与新消息恢复都不遗漏、重复或跳回顶部。
- 本人未以个人加入，但可代理团队：从团队工作区查看和发言成功；不出现可用的个人发送选项。
- 属于团队但没有代理权限：能看见符合业务规则的说明，不能读群或发言；不能靠直调接口绕过。
- 群审批中、拒绝、已加入、撤销、重复点击、多员工同时邀请：状态真实且幂等。
- 上传中切换身份、发送时权限回收、离线重试、账号切换、网络未知结果：原身份固定，草稿可恢复。
- 团队首次加入和重新加入不泄露加入前消息；原文链接、搜索、统计、导出也遵守可见范围。
- 相同群的个人入口和团队入口不重复写消息，不重复通知；自己的／同事的消息底色正确。
- 宽窄窗口、暗色、键盘菜单、退出重开；消息详情、延展、转发、表态和已读体验尽量复用普通群。
- 接口未部署时仍保持当前明确的开发中提示，不伪装入群成功、不显示“已同步”。
