# Arko 想法回复：后端协同交接

用户要求：详情侧栏中，普通延展和 Arko 想法都可点击回复，底部显示被回复者与引用预览。回复记录应能回到正确的父级，跨端重新加载仍保留关联。

## 本地前端已实现的范围

- 普通延展复用现有 `source.message-extension.extend`，发送时带真实的 `parentRecordUid`。
- 普通延展与 Arko 共用选中、键盘操作、引用预览、输入聚焦、切换与取消时保留草稿的交互。
- 详情原消息下方重复的评论角标已去除；主对话中用于进入评论的入口保留。
- Arko 想法可选中并输入，当前明确提示暂不能发送；按钮及提交函数均阻止写入。没有把 thought ID 冒充 Record UID，也没有悄悄改成回复原消息。
- 本次未修改后端代码，也未通过真实账号发送测试评论或触发 AI 生成。

## 已核实的合同边界

核验的是本地代码，不能据此宣称线上不存在其他能力：

1. 插件 `src/record-thought-contract.ts` 提供 `id / recordUid / scene / generation / visibility / content`，其中 `recordUid` 是原消息身份，没有想法自身的可写消息引用。
2. 插件 `ChatService.extendSourceMessage` 仅允许把原消息或其真实延展树内的 Record 作为父级；不在树内的 ID 返回 `source-message-extension-target-invalid`。因此不能直接传 thought ID。
3. 所查 `jotmo-intelligent` 提交 `6c096ba6` 的 `gin/api/router.go` 中，`/thought` 与 `/chat-thought` 对外注册的是查询接口，未找到想法回复创建接口。
4. 移动端现有 `RecordThought` 模型同样未提供可直接复用的回复引用。若已有线上能力，请先提供正式合同与脱敏响应，再复用，避免重复建设。

## 请后端确认或补齐

### 1. 可回复身份与能力

建议查询结果提供 owner 签发的 `replyTargetRef`，并明确当前场景是否可回复；最终字段名以正式合同为准。引用至少绑定登录用户、消息容器、原消息、想法场景、代际或版本及可见范围。旧的私人想法查询还需提供可冻结的版本身份。

现有 `id`、客户端提供的正文或普通 `parentRecordUid` 不能作为授权依据。未返回可验证引用与能力时，前端继续保持不可发送。

### 2. 创建回复与长期关联

建议在既有回复命令中增加有类型的目标引用，或提供正式的想法回复命令；不要让客户端猜测 parent UID。

- 请求承接可验证目标引用、正文、附件、mentions，以及客户端 `recordUid / relationUid` 幂等键。
- 返回真实回复记录、父级类型与身份、冻结的被回复内容及可见范围。
- 详情树/回复查询需能重新读取这种关联，分页、合计、嵌套展示和跨端一致。
- 相同幂等键重试不能重复创建；未知结果应可用原幂等键核对。
- 想法被重新生成、失效、删除或撤权后，明确旧引用的读写规则，禁止无提示改挂原消息。
- 明确回复是否会触发 Arko 再次生成，复用既有模型、费用准入和幂等触发规则；仅保存用户回复与再次调用 AI 是不同动作。

### 3. 私密与群聊边界

群内仅本人可见的 Arko 想法，其回复与引用正文不能进入群公共消息流。公开回复、私密回复必须由服务端校验读写域，不能相信客户端 `visibility`。成员离群、撤权、账号切换及签名跨容器重放均须拒绝或按合同安全降级。
