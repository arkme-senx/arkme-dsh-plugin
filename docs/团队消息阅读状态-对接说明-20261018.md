# 团队消息阅读状态：前端对接与后端待核对项

更新日期：2026-10-18。范围：Arkme 插件的团队消息通道；不涉及普通群聊或广播频道。本轮没有修改、发布后端。

## 已接通的能力

现有 `POST /api/v1/team/conversations/read-receipts/query` 已可返回逐个团队成员的阅读状态；基础功能不需要等待新增接口。

内部团队视图：

- 外部用户发来的消息：常驻「团队已读 X/Y」入口，点击查看成员姓名及已读/未读。
- 团队发送的消息（本人或其他同事发出均支持）：常驻「对方已读/未读 · 团队已读 X/Y」，详情分别列外部联系人与内部成员。
- 已读后入口继续保留；支持全部、已读、未读筛选。
- 发送者不计入接收者统计。内部消息 5 人团队发送者排除后是 4 人；外部来信是 5 人。
- 稳定身份由服务端成员 user_id 派生账号隔离的 opaque key；同名不同人不合并，分页中同一人不重复计数。
- 外部视图继续仅保留聚合的团队阅读状态。插件 Host 即使收到多余成员数据也不向外部视图透传名单或成员分页游标。
- 读状态与列表加载分离：只查询可见消息及打开的详情，最多 2 个并发请求；同消息合并请求，15 秒缓存/可见且聚焦时轮询。轮询不调用 timeline，不重置滚动或输入。
- 打开详情和显式重试会刷新；后台失败保留上次名单并提示重试，失去权限/账号变化清除名单并终止旧请求。
- 不修改现有 read/advance 触发规则：页面可见且聚焦、列表底部可见才推进阅读游标。

## 实际使用的字段与边界

| 数据 | 当前用途 |
| --- | --- |
| timeline.messages[].side | 区分团队发送与外部发送 |
| timeline.messages[].actor_user_id | 仅在加密引用内部保存，用于排除发送者；不直接暴露原始身份 ID |
| receipt.members[].user_id | 稳定身份与去重，用于判定当前用户 |
| receipt.members[].identity | 现有头像/显示名呈现 |
| receipt.members[].read | 只有布尔值才视为有效已读/未读，缺失时显示状态待同步 |
| receipt.visitor_read | 团队发出消息的外部联系人状态 |
| receipt.team_read | 对外聚合的团队阅读状态 |
| receipt.has_more / next_cursor | 加载更多成员；未取完整时只显示已加载人数，不假装总人数 |
| receipt.members[].read_at | 暂不在新详情中展示具体阅读时刻，先核实其服务端语义 |

仅在成员完整、均有稳定身份和明确 read 布尔值、可确认发送者已排除时统计 X/Y。接口不完整、分页游标不推进时明确报错；不能把未知当未读或把第一页当全部。

- 团队发送均返回 4 位已读接收成员，正确排除原发送者；含本人和其他团队成员发送的消息。

- 外部来信可展开团队 5/5 名单；未读筛选显示空结果，状态入口保持存在。

## 后端建议核对/后续优化

这些不阻塞当前小团队的基础名单展示，但应在协议中明确：

1. **成员集合语义**：返回的是当前团队成员，还是消息发送时的接收成员？新加入、已离队、禁用成员如何处理？建议返回明确的接收者集合/统计口径；避免新成员被算成历史消息长期未读。
2. **分页一致性**：为多人团队提供 snapshot_revision 或稳定游标视图，避免读状态/成员变化时跨页遗漏或重复；响应每页都明确 has_more、next_cursor。插件可去重，但无法从缺失页恢复真实总数。
3. **汇总与批量查询**：timeline 中可加独立的 receipt_summary，或提供一批 message_uid 的汇总接口，返回 recipient_count / read_count / unknown_count（已排除发送者）。目前逐消息查询已限并发、仅可见行轮询，但大团队应避免逐条全成员查询才能算总数。
4. **实时事件**：确认 read/advance 后是否向有权限的内部客户端发布独立的阅读状态变更事件（conversation_uid、side、message_uid 或 read_seq、revision）。前端可只失效阅读状态缓存，避免触发全会话重读。当前有 15 秒轮询兜底，不宣称已有逐消息实时推送。
5. **时间语义**：明确 read_at 是成员最后阅读游标更新时间，还是本条消息首次被读的时间。若是前者，不应标作这条消息的准确已读时间。
6. **身份与缺失状态**：内部 timeline 保证 actor_user_id，成员列表保证 user_id 及布尔 read；发送者身份缺失时，插件不会猜测排除对象或人数。
7. **鉴权**：服务端持续校验当前成员关系，不能仅依赖前端 side 或本地缓存；外部用户不得通过 receipt 分页获取内部成员名单。

## 联调验收建议

- 外部发一条消息后，仅内部甲阅读：甲已读，乙未读；外部只看到团队已读。
- 内部甲回复后：甲不在接收者分母内；外部联系人和内部乙的阅读状态独立变化。
- 内部乙回复同样可查，不能只支持当前用户自己发送的消息。
- 全员已读后仍能打开详情；新状态更新不改变正在看的消息、滚动位置和输入焦点。
- 50 人以上团队验证分页、重名成员和成员变更；权限撤销、切账号后不得显示旧名单。
- 接口超时或缺字段显示状态未知/待更新，不能全算未读。
