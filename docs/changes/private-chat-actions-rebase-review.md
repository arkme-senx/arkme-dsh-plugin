## 2. 仍成立的根因

- 菜单在首次打开或重置后主动调用 related-recordings.eligibility 和 user-ban.status，并渲染检查文案。同一会话成功结果会被复用，不是每次打开都重新请求。
- 相关录音资格只查询 Backend able-func 17，不直接检索 Audio。实际列表另有权限检查与 Chat 分页，不能为菜单提前加载列表。
- 封禁状态先经 Chat 成员查询确定有效对端，再查 Backend。不能用浏览器 peerUserId 或一个旧 sourceRef 签名替代当前会话访问校验。
- user.profile 调用的是 cachedProfile，通常返回持久化缓存；菜单只在 profile 为空时强制刷新，不能用它证明角色新鲜。
- related-recordings.eligibility/page 的 Host 分发未透传 requestSignal。
- 拒收将 loading 与 mutating 合成 busy，后台刷新也使已有值的按钮失效；缓存键采用变化的 sourceRef。
- 封禁失败只显示错误，旧 ready 快照继续复用。Backend 已有“Mongo 已写入、Redis 投影发布失败则返回失败”的明确行为和测试。

主要证据：[菜单](../../src/client/ArkmeSidebar.tsx)、[资料服务](../../src/services/profile-service.ts)、[Host 分发](../../src/host-api.ts)、[拒收 Hook](../../src/client/direct-message-admission.ts)、[封禁服务](../../src/services/user-ban-service.ts)、[相关录音服务](../../src/services/related-recording-service.ts)。

## 3. 对上一版方案的必要修订

### 3.1 不在每次刷新时撤掉已有的有效身份

“每次打开先隐藏员工项，等完整 user.profile.refresh 返回再出现”会把文字加载改成项目闪现，不符合热打开稳定的目标。完整资料刷新还等待公开头像资料补全；不能把它放到每次开菜单的前置阻塞链中。

推荐：账号生命周期拥有一份本次登录、当前环境/Provider 下经服务端确认的身份快照。登录/进入有效账号后预热，恢复前台及过期时刷新，刷新时不要把仍有效的快照清成 unknown。菜单状态每次打开刷新；身份资源按自己的新鲜度策略管理，不为每个菜单项重复拉完整资料。

身份规则：

- 未确认、跨账号、跨环境、跨登录代次、Provider 变更后的身份不能授予员工可见资格。
- 持久化旧 profile 可用于头像昵称展示，不能直接授予新登录的员工可见资格。
- 初始建议将展示身份的有效期上限设为 60 秒，与当前 Profile 服务已有缓存量级一致；这是一项设计参数，不是权限实时性的证明。过期或明确失效后未核验成功则隐藏受限项。
- 接收到当前账号普通身份或权限撤销结果后，立即移除员工项、取消尚未提交的员工动作。请求失败不能把 unknown 写成“确认是普通用户”，但不能延长已失效的员工展示资格。
- 员工状态查询和写入继续由 Backend 校验实时员工/账号状态，浏览器身份不授予服务端执行权。

必须明确的边界：上述策略保证普通账号不因默认值、其他账号缓存或未核验的历史角色误显；角色在服务端刚被撤销而客户端尚未获知时，仍可能短暂显示入口。现有链路没有可证明实时到达的角色撤销事件。若产品要求此场景也零延迟消失，就不能同时承诺旧角色缓存即时展示；必须选择实时核验/失效协议，并接受相应延迟与跨仓范围。不能在“只有员工可见”这句话下面隐藏这个取舍。正式实现前须沿用或明确记录这个产品边界，不能擅自宣传绝对实时保证。

### 3.2 请求代次不是业务版本

scope/request/mutation generation 只能防止本地旧请求覆盖新操作，不保证服务端响应的业务事实没有回退。拒收有 ownRevision 与 counterpartRevision 两个独立版本；不能按客户端返回时间盲目覆盖。

资源适配器负责版本接受策略：完整验证后，新快照两边版本均不低于已知值才可替换；更旧或不可比较的快照保留最后可用值，标记待核对，最多合并一次后续刷新，不无限循环。不要在通用 Store 中拼接两个不同响应来伪造完整准入投影。版本相同不代表 rollout 开关不会变化，开关按有效的新响应更新。

封禁公开响应没有 CAS revision；updatedAtMillis 不是可靠的唯一版本。第一版保留现有显式设定状态/服务端最后写入语义，不伪造 CAS，不宣称解决多管理员并发冲突。

### 3.3 不把三项菜单做成一个通用业务框架

保留三层职责，不要求三层一定只有三个文件：

1. 轻量共享资源 Store：快照、请求合并、失效、订阅、作用域与写入屏障。
2. 私聊操作 Controller：静态类型化注册表、业务适配器、统一执行锁和反馈。
3. 菜单组件：展示、定位、焦点与可访问性。

不需要独立的万能工作流引擎、依赖图执行器、服务端动态菜单协议或新的全站缓存平台。确认、版本冲突、危险操作重试仍属于业务适配器。统一的是生命周期和 UI 合同，不是强迫不同业务使用相同成功/失败语义。

## 4. 数据与接口归属

| 资源 | 客户端 key | 真正 owner / 读取入口 | 展示默认值 |
| --- | --- | --- | --- |
| 当前身份 | accountScope + loginEpoch | Profile / user.profile.refresh | unknown，受限入口隐藏 |
| 相关录音资格 | accountScope | RelatedRecordingService / eligibility | 无已知值则隐藏 |
| 拒收准入 | accountScope + sourceKey | Chat / chat.direct-message-admission | 未勾选；不是一份伪造的完整 admission |
| 对端封禁 | accountScope + sourceKey | UserBanService / user-ban.status | 员工门槛通过后显示“封禁用户” |

accountScope 至少隔离环境、用户及 Provider 上下文；退出/重新登录即使回到同一用户，也需要新的本地代次。不要直接把 authStore 每一次刷新 revision 当作账号变化，否则普通刷新也会清空所有缓存。

sourceRef 是最新请求凭据，sourceKey 是稳定缓存身份；引用变化不清空同一会话的业务值，但需要更新后续请求绑定。首次缺少稳定 sourceKey 时可暂用 sourceRef 隔离，不能跨会话猜测合并。

Store 保存 value/origin/validatedAt/refreshing/error/pending/generation，不保存默认值为成功事实。禁止菜单拿 fallback 构造 canSend、expectedRevision、员工资格或 rollout 权限。

每个资源只有一份客户端事实快照。拒收 Hook 改为该资源的订阅适配器；输入框和菜单订阅同一份事实。原来的发送前检查及服务器最终准入保持不变，不能为了展示未勾选而放开已知拒收。保留草稿、旧消息编辑/撤回、附件及多目标转发的既有边界。

## 5. 查询、取消和缓存策略

- 每次打开菜单刷新适用的菜单业务资源；相同资源进行中则加入同一轮请求。资格失败不阻断拒收，封禁失败不阻断其他项。
- 账号级 eligibility 仍需要有效私聊 sourceRef 调用现有接口；不是登录时无会话即可调用。请求资源 key 与请求参数不必相同。
- 身份在账号生命周期预热；封禁不为所有私聊批量预取，只有使用菜单且具备可见资格时查询。
- 默认使用内存缓存。拒收保留已有持久化恢复，通过可选存储适配器迁移；旧 key 仅在当前账号/当前引用精确匹配且数据验证通过时读取。写入新版成功前不清理旧缓存。
- 新 Store 有不活跃条目的容量上限和淘汰规则。不能无限累积 sourceRef、Promise 或监听器。
- 当前 SDK 请求取消只退出消费者等待，与共享请求是否继续是两回事。共享读仍被其他消费者使用时不能被某个菜单关闭误杀；账号/Provider 失效由 owner 统一取消并禁止旧结果落地。
- 修复 related-recordings 两条既有路由的取消透传。不要误把请求协调器有意保留共享请求的行为也改成“任何消费者退出都取消”。
- 查询开始时记录 mutationEpoch；操作开始提升该代次并使旧查询失效，操作中失效事件记为 dirty，结束后合并刷新。
- 网络层继续使用现有请求协调器限流。不要顺手给菜单读接口加第二份 TTL 结果缓存；bypassCache=true 也仍可能加入既有 in-flight，请求代次不能只在浏览器改变、Host 却复用写前旧请求。第一版在客户端做菜单读合并，沿用当前未设置共享 key 的业务读取，避免制造这一新竞争。

缓存改善的是感知等待，不保证减少请求。与当前同一会话成功后不再查询相比，“每次打开刷新”会增加请求量。员工菜单的封禁读取本身有 Chat+Backend 两跳；身份刷新还可能带头像补全。验收必须记录请求数和慢接口隔离，不能宣传所有场景既更快又更省请求。

## 6. 操作合同

注册项必须显式声明 id/order/kind/applicability/visibility/resource/fallback/presentation/intent/execute/invalidates。漏写 visibility 不允许默认公开。新增简单功能仅增加定义与业务适配器、测试，不修改公共 Store 或菜单组件中的功能分支。

执行流程：捕获稳定 actionId/账号代次/目标/用户所见动作 → 单项同步锁 → 必要核验/确认 → 显式命令 → 回执处理。

- 用户点击“拒收”就是 refused=true，查询到已拒收时不能改为解除；已达目标可刷新显示并说明无需重复设置。
- 拒收必须使用真实 expectedRevision；冲突后显示最新状态并由用户重新决定，不静默重试新版本。拒收创建开关关闭时，只禁止新增，不禁止解除已有拒收。
- 封禁/解封使用明确目标命令和已有确认。不要用刷新后的 banned 再取反；不要用默认展示伪造 exists、历史备注、目标资料。
- 操作成功用服务端回执更新缓存；后台查询不覆盖回执。当前源离开后不能给新会话弹成功提示，也不能把请求取消当作服务端事务回滚。
- 失败区分确定业务拒绝、版本冲突、结果未确认，不能统一自动重试。未提交的确认取消不触发后台写。
- Host 当前未完整透传 writeOutcomeUnknown；第一版不依赖不存在的浏览器字段。对于已经发出的、不足以证明未执行的错误，保留原命令并核对；未知错误不能伪装成已回滚。
- Backend 封禁 Mongo 成功但 Redis 失败时，只查询 Mongo 不能证明访问控制已同步。需要用户明确重试同一个显式命令，不能见到新状态就提供反向动作作为“恢复”。拒收不能套用这条无版本重试策略。

## 7. 菜单交互合同

- 有可展示项时，点击后直接显示缓存/默认态，不等待网络，不显示查询中的转圈、骨架、检查文案。
- 员工资格未确认或已失效时不显示员工项。有效资格刷新中不反复移除再插入。无资格的普通用户不因封禁状态的默认值出现员工操作。
- 没有任何可显示项时显示明确的“暂无可用操作”默认空态；权限结果回来后更新，查询失败有重试出口，不出现空白浮层或永久无入口。
- 普通状态刷新不禁用已知状态的操作；真正提交时只锁对应项。焦点、业务作用域和操作意图独立于标签更新。
- 以稳定 id 更新菜单，保留标准注册顺序，不采用“按接口返回先后追加、下次再重排”的不稳定方案。
- 更新可能增加/移除权限控制项。指针按下或键盘激活时捕获对应动作；结构变化不能把同一个释放事件交给另一个项目。必要时取消这一手势，不能执行另一操作。焦点因权限移除必须安全回到触发按钮或存续项。
- 固定锚点，按实际内容测量位置；不用硬编码功能数量估算高度。不能承诺动态权限改变时菜单几何尺寸永远不变，但必须保证不误点、不抢焦点。
- 用户未触发修改时不弹全局 toast；后台查询失败保留最后可用展示并提供局部反馈。权限类失效不能以“保留旧值”为由继续授权。

## 8. 实施顺序与范围

1. 固定行为测试和新鲜度边界，先验证菜单默认为结果态但不授权。
2. 建立轻量资源原语、账号身份资源和私聊操作 Controller。
3. 迁移拒收 Hook，保留输入框、持久化、实时失效和发送合同；不得保留两个并行事实 owner。
4. 接入 related-recordings 和 user-ban 的声明式适配器，统一菜单渲染与执行锁，删除旧散落状态。
5. 补齐既有取消链，完成竞态、身份与交互回归。
6. 通过类型检查、相关与全量测试、构建，再用隔离运行时/制品做冷暖、普通/员工、慢网/离线场景验收。

主体只改插件，不改 Audio 和 Backend 业务合同，不改 DSH。复用公开 Host/SDK/Tools；此次不新增业务查询或权限协议，既有消费面须回归。若后续新增轻量角色接口、角色推送或封禁 CAS，则作为显式合同扩展同时覆盖 UI/SDK/Tools/Host，不能塞进纯菜单重构。

回退方式是恢复组件/适配器代码，不能回退服务端已经执行的拒收/封禁事实。新缓存格式可忽略，不提前删除旧拒收缓存，不做不可逆持久化迁移。

## 9. 验收矩阵

| 维度 | 必须通过的场景 |
| --- | --- |
| 身份隔离 | 普通用户、未知身份、持久化旧员工资料、员工→普通账号、跨环境同 ID、同账号重新登录、Provider 重启 |
| 可见性新鲜度 | 本次登录已验证员工热打开稳定；身份过期/失败隐藏；收到撤销结果立即移除；不宣称未收到的远端撤销已实时生效于 UI |
| 默认展示 | 无缓存、离线、已知拒收、仅对方拒收、相关录音 denied/error、无可显示项 |
| 请求 | 每次打开按合同刷新、同资源合并、共享消费者取消、账号级资格跨会话、Host 取消透传、限流及失败冷却 |
| 竞争 | A→B→A、sourceRef 更新、读晚于写回执、失效发生在操作中、业务版本回退/不可比较、连续点击、确认期间切换 |
| 写入 | 明确目标不反转、拒收 CAS 冲突、创建开关关闭仍可解除、封禁回执丢失/Redis 失败、确定拒绝不盲重试 |
| 编辑器与消息 | 草稿保留、输入中提示、已知拒收禁止新发送、未知状态保持既有服务端兜底、历史编辑撤回、附件及多目标部分成功 |
| 交互 | 键盘导航/Escape/焦点恢复、权限增删、标签更新期间点击、菜单定位、普通失败不全局打断 |
| 扩展性 | 注册第四个测试项只添加定义/适配器/测试，公共 Store 和菜单组件无需增加业务分支 |

- 6 个临时诊断用例通过，确认：旧角色缓存不按年龄刷新；完整资料刷新等待头像补全；当前拒收 Hook 接受较低版本的模拟响应；未知拒收恢复按查询状态取反；两条 related-recordings 路由丢失取消信号。较低业务版本的用例说明客户端缺乏保护，不证明线上实际发生过服务端版本倒退。
- Backend `go test ./internal/userban` 通过，包含写事实后投影发布失败及显式幂等重试。
- 临时诊断测试已删除，避免把“断言旧缺陷存在”的测试留作长期 CI 合同。

本轮未实施新架构、未跑全量构建/制品/UI E2E，因此不能标记实施验收通过。此文档是下一步开发和验收的依据，不是“绝对最优、零风险”的证明。
