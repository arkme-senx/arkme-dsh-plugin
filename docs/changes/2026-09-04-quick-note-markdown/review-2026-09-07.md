# Markdown 实现审核（2026-09-07）

本轮确认 7 个可复现问题：1 个 P1、6 个 P2。建议先修复粘贴时的内容转换，再处理转发原文保留和两端解析一致性。仅审核，未修改业务代码；临时复现测试已从仓库移出，保留在文末证据目录。

## 审核范围与方法

- 对比 Arkme Harness 插件 `arkme-dsh-plugin` 和 Flutter `jotmo_frontend` 当前工作区的 Markdown 改动，包括未跟踪的新文件；核对 Record 提交 `95537f1` 和 Chat 提交 `4356ccf` 中相关后端改动。
- 按“编辑器输入/粘贴 → 序列化 → 发送 payload/标签索引 → 后端保存/转发 → 桌面与移动端阅读”的顺序追踪数据；对照本目录 proposal、design、spec 的已确认范围。
- 桌面使用实际 Tiptap 组件、真实草稿 store 和剪贴板事件复现；链接使用实际 `ArkmeMessageContent` 详情入口。移动端使用实际 `RecordMarkdownBody` widget 和公开的转发投影入口复现。
- 只运行相关既有测试和补充的最小复现，未执行测试服真实发送、双端同步或设备交互验收。

## 1. [P1] 粘贴处理忽略光标上下文，拆分段落并错误解释代码

位置：[ArkmeMarkdownComposerInput.tsx:49](/Users/zhou/Desktop/project/jotmo/worktree/v143/arkme-dsh-plugin/src/client/ArkmeMarkdownComposerInput.tsx:49)。

复现一：输入 `甲丙`，光标放在两字之间，粘贴 `乙`。预期发送源码为 `甲乙丙`，实际为 `甲\n\n乙\n\n丙`，变成三段。

复现二：用代码围栏和 Shift+Enter 进入代码块，粘贴 `# 标题\n**代码**`。预期代码正文逐字保留，实际编辑器文本为 `标题代码`，井号、星号和换行被作为 Markdown 结构消费。

根因：所有 `text/plain` 粘贴均调用 `insertContent(..., { contentType: 'markdown' })`，先解析成完整块结构，没有根据当前段落、行内代码或代码块决定插入方式。影响输入内容以及后续序列化结果，不只是视觉样式。

修复方向：代码上下文按字面文本插入；普通段落内单段文本按光标位置合并，结构化 Markdown 粘贴保留合理的块级插入行为。两类复现需分别覆盖。

## 2. [P2] 移动端转发解析提前 trim，破坏 Markdown 缩进

位置：[chat_record_content_projection.dart:2205](/Users/zhou/Desktop/project/jotmo/worktree/v143/jotmo_frontend/lib/features/chat/application/chat_record_content_projection.dart:2205)，新增格式接入位于 [2406 行](/Users/zhou/Desktop/project/jotmo/worktree/v143/jotmo_frontend/lib/features/chat/application/chat_record_content_projection.dart:2406)。

复现：给 `ChatRecordContentProjection.fromRecordPayload` 传入 `forward_records`，其中一条为 `text_format: markdown`、`text: "    code\n"`。投影得到的 `.text` 为 `code`，前导四空格及尾部换行已丢失，缩进代码块会按普通段落显示。

根因：`_payloadString` 和 `normalizeChatForwardRecordTextSeparators` 在识别格式前已执行 trim；此次新增的 `summaryText`、`toRecordSnapshot` Markdown 分支位于其后，无法恢复原文。同一旧清理函数还会将字面的反斜杠 n 替换成换行，应一起检查代码内容保真。

修复方向：读取条目时先确定格式，对 Markdown 保留原始字符串；纯文本兼容清理继续走原分支。

## 3. [P2] URL 片段被写入业务标签元数据

位置：[markdown.ts:60](/Users/zhou/Desktop/project/jotmo/worktree/v143/arkme-dsh-plugin/src/markdown.ts:60)，写入入口为 [chat-service.ts:102](/Users/zhou/Desktop/project/jotmo/worktree/v143/arkme-dsh-plugin/src/services/chat-service.ts:102)。

复现：`arkmeMarkdownHashTagRanges('https://example.com/#fragment')` 返回 `tag: fragment, startIndex: 20, length: 9`，预期无标签。

根因：文本范围遍历跳过代码、图片等节点，却继续进入 GFM 自动链接的文本子节点；保存时再用普通标签扫描器识别井号。因此 URL 的 fragment 被放入 `hash_tags`，也会被个人/主题快记的标签同步逻辑使用。编辑器装饰和阅读 AST 已排除链接，造成显示与保存不一致。

修复方向：标签提取明确排除链接/URL 上下文，复用与编辑器、阅读一致的规则；增加裸 URL 和带 URL 标签文本的测试。

## 4. [P2] 转义字符污染标签名，移动端又截断同一个标签

位置：[markdown.ts:75](/Users/zhou/Desktop/project/jotmo/worktree/v143/arkme-dsh-plugin/src/markdown.ts:75)，移动端 [record_markdown_body.dart:151](/Users/zhou/Desktop/project/jotmo/worktree/v143/jotmo_frontend/lib/features/record/presentation/record_content/record_markdown_body.dart:151)。

复现：在桌面逐字输入 `#a*b `，可见文本为 `#a*b `，保存源码为 `#a\*b `，提取的标签名却是 `a\*b`。移动端渲染同一源码时无法生成完整的 `#a*b` 标签控件。

根因：保存端直接扫描 Markdown 源码片段，将转义反斜杠混入业务标签名；阅读端会显示解码后的文本。移动端另用排除星号和反斜杠的正则扫描源码，与既有标签边界规则不同。结果是标签索引、显示名称和点击搜索词不一致。

修复方向：分离解码后的业务标签名与原 Markdown UTF-16 范围；移动端复用相同语义边界，跨端 fixture 增加带转义标点的标签。

## 5. [P2] 移动端块级 HTML 原文和内部正文消失

位置：[record_markdown_body.dart:93](/Users/zhou/Desktop/project/jotmo/worktree/v143/jotmo_frontend/lib/features/record/presentation/record_content/record_markdown_body.dart:93)。

复现：标记为 Markdown 的正文为 `<b>保留 HTML</b>\n\n<div>块级 HTML 正文</div>`。实际 widget 可见文本只有 `<b>保留 HTML</b>`，整个 div 块连同内部正文未显示。

根因：移动端只补充了图片字面量和业务 inline syntax，没有将块级 HTML 变成可见文本；默认解析/渲染链路忽略该块。桌面已有 HTML 节点转字面文本的处理，因此同一份源文在两端显示不一致。

修复方向：按已确认规则，将不支持的 HTML 保留为源字符显示，涵盖块级 HTML。本问题不要求支持 HTML 排版或执行 HTML。

## 6. [P2] 移动端链接里的井号文本覆盖正常链接点击

位置：[record_markdown_body.dart:155](/Users/zhou/Desktop/project/jotmo/worktree/v143/jotmo_frontend/lib/features/record/presentation/record_content/record_markdown_body.dart:155)，点击行为位于 [176 行](/Users/zhou/Desktop/project/jotmo/worktree/v143/jotmo_frontend/lib/features/record/presentation/record_content/record_markdown_body.dart:176)。

复现：渲染 `[#标签](https://example.com)`。链接标签内生成一个业务 `InkWell`，其 onTap 明确调用 `openMobileSearchForRecordTag`，而非正文链接的打开地址逻辑。widget 测试确认了该控件；点击行为由回调代码确定，本轮未实际弹出搜索页面。

根因：业务 inline syntax 未排除 Markdown 链接标签上下文，自定义 widget 接管了点击。桌面业务节点遍历显式排除了 link/linkReference，因此两端行为不同。

修复方向：链接中的业务样式不可覆盖链接目标；解析时排除该上下文，或让自定义构建继承父链接行为。

## 7. [P2] 桌面详情的带格式分享链接丢失标签文字

位置：[ArkmeMarkdownBody.tsx:76](/Users/zhou/Desktop/project/jotmo/worktree/v143/arkme-dsh-plugin/src/client/ArkmeMarkdownBody.tsx:76)。

复现：通过真实 `ArkmeMessageContent` 的 `presentation="detail"` 渲染 `[**重点链接**](https://jiwo.cc/s/0123456789abcdef)`。预期保留“重点链接”，实际显示 URL，输出中不含原标签文字。

根因：链接标签只收集顶层 string children；strong/em/code 等 React 子节点被直接过滤，之后 `label || href` 回退为地址。生产中的分享链接自定义渲染器使用该标签，故详情入口受影响。普通网页链接若回退到原生 a 标签，其 children 仍保留，不应扩大为所有链接均丢失。

修复方向：从嵌套节点完整取得可见标签，或让自定义链接渲染保留原 children。
