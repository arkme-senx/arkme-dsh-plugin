# 团队入口加载时的请求调度修复

## 问题与证据

官方团队成员在启动后点击“联系作者”，应打开团队收件箱。空收件箱本身是合法结果，不能通过跳过权限检查或改成外部用户会话解决加载问题。

现场分段计时及真实 ServiceRuntime 回归测试确认三条独立链路：

- 内置通知中心展开世界互动详情，并与头像等后台读取并发占用浏览器 HTTP 连接。团队打开请求已被 JavaScript 发起，却曾在发送前等待约 2.3 秒。
- 通知列表、归档列表及归档状态的复合 owner 与其内部 HTTP 读取重复占用 interactive-read 额度。两个实际读取可以占满四个传输槽，使团队读取排队。受控测试在旧实现上复现，在子请求未完成时验证修复后团队请求可以发出。
- 世界互动详情的 `/api/v1/public-record/extend-list` 漏传读取 lane，落入默认 write。现场团队打开请求等待写额度约 542 毫秒，而网络请求约 40 毫秒。该接口后端只做查询及数据投影，同接口其他调用已按读取处理。

上述时间来自不同采样，不应相加。单次未完整埋点的延迟不能全部归因于其中任意一项。

## 实现边界

- 内置 UI 的明确后台读取复用 ArkmeRequestCoordinator，在浏览器发起请求前共用两个并发名额。只作用于明确标记且位于读取白名单中的操作；前台操作、发送、未知操作及公开 SDK 调用路径不变。不引入缓存、合并或重试。
- 后台请求绑定当前账号与环境，排队期间或执行期间切号即取消，并拒绝迟到结果。调用方取消及世界互动读取的 Host 断连信号继续传递至网络层。
- 复合 owner 保留按 route 的队列、速率、并发、总时限、恢复、失效与合并；真实传输由子请求占用 lane/service 额度。直接发起传输的 owner 不变。
- 世界互动详情只显式改为 interactive-read，不将其加入自动重试目录，不改变真实写请求的重放语义。
- 官方目标识别、成员权限、会话打开写语义和消息发送逻辑不变。没有修改移动端、DSH 或服务端。

## 审查发现与修复

后台限流接入后，官方通知与群互动目录原来共用的刷新入口也把用户重试、加载更多放入后台队列。真实 Client API 与调度器的受控测试确认：两个未完成的头像读取占槽时，这些显式操作不会下发，存在可见的等待；不是通过按钮文案推测的问题。

- 官方通知的自动首次加载、定时及焦点恢复仍走后台；重试、更多及标记已读后的结果校准走前台。同一前台读取合并重复点击；前台操作可取消并替代等待或执行中的后台读取，整轮分页保持同一优先级。
- 读取取消与标记已读写入使用不同的控制器，提升读取优先级不会取消写入。账号、代次和请求身份共同阻止旧结果及旧清理逻辑覆盖新请求；真正的数据失效事件仍触发一次后续校准。
- 通知自动恢复保留已有错误入口，“加载更多”只在前台操作期间禁用，确保用户在后台排队时仍有可用的主动恢复路径。
- 群互动目录的重试直接交给当前账号的查询 owner，不再通过全局失效事件发起。保留原分页、版本冲突恢复及权限重验，全程使用前台优先级；普通自动事件继续后台串行合并。

这次修复仅调整两个内置 UI 读取 owner 的调度和生命周期，不放宽权限、不新增缓存，不修改发送或持久化契约。

## 头像等待依赖的修复

后续受控测试确认另一个后台调度接入后的回归：`ArkmeCallSurface` 的五处读取及 `OutgoingCallRuntime` 原来等待头像后才发布业务结果。两项无关后台读取持续占槽时，冷头像无法开始，导致通话记录、联系人、搜索或拨号也等待。修复不提高所有图片的请求优先级，而是移除可选图片对业务结果的前置依赖。

- 通话记录首载/刷新/更多、私聊联系人、官方联系人和搜索结果在原取消及代次检查后立即发布；现有 `CallAvatar` / `useArkmeAvatarImage` 订阅共享 store，缓存直接显示，缺图异步补齐。删除重复预热 helper，未新增缓存。
- 呼出 prepare 成功后同步启动原 store 的非阻塞预热，立即登记租约并启动心跳、初始化引擎。发出唯一一次 `call` 前使用 store 的 `current()`；也可使用引擎初始化期间已完成的缓存。没有头像则使用默认头像，迟到下载只进入缓存，不回写通话状态、不重发拨号、不新增桥接协议。
- 取消边界测试同时确认基线已有问题：bootstrap 后取消、引擎的 `ready` 在终止宽限期迟到时，仍可能发送 `call`。现在首次拨号必须处于 `bootstrapping`，取消后的 `ending` 不允许拨号，现有终止宽限与租约释放不变。
- 内存缓存、不可变图片的浏览器持久缓存及 Host `cacheOnly` 本地探测均沿用原设施；命中时不占新增后台下载额度。同 cacheKey 的 `pending` 仍在排队前去重。profile/bot 的 Host 缓存只有请求抵达 Host 后才能判断，客户端冷读仍可能先排队；本轮不改变其授权和持久化语义，也不把团队签名头像混入普通附件缓存。

验证覆盖：`call-surface-interaction.test.tsx` 的 deferred 图片首载/分页/联系人/搜索、迟到补图及切换/卸载；`outgoing-call-runtime.test.ts` 的缓存、心跳、失败、取消/卸载/切号、迟到 ready 及不重复拨号；`outgoing-call-avatar-priority.test.ts` 使用真实共享 store、Client API、调度器和通话 runtime，仅替换 SDK 数据，验证两槽占满仍能拨号，以及缓存命中、本地探测和八次同图读取只下载一次。

本轮遵从用户要求进行代码验收，不启动运行实例或读取凭据。

本轮结果：先以 deferred 头像和取消后迟到 ready 复现失败，再修复；相关六个文件 93 项测试通过。独立复审未发现新增成立问题；类型检查通过；最终全量 894 个测试文件通过、12 个跳过，10,612 项通过、16 项跳过；最终构建与打包通过。真实调度器集成测试只使用 SDK 内存 fixture，Host 本地探测响应也来自 fixture，不宣称完成生产或真实 Host 图片下载验收。
