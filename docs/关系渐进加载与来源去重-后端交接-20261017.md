# 关系渐进加载与来源去重：后端交接

日期：2026-10-17（CST）。本轮只修改 Arkme 插件，不修改或部署后端。

## 问题与实测

用户反馈探索 → 关系列表、人物详情长时间等待，相关记录中同一原文重复占据卡片。2026-10-17 01:58–02:04 使用 3102 同一账号进行只读测量：

| 请求 | 单次耗时 | 观察 |
| --- | ---: | --- |
| 插件 `explore.list` | 7,009 ms | 首批 50 条；总实体 7,154 |
| 插件周鹏 `explore.detail` | 26,603 ms | 30 条提及仅对应 28 个原始来源；一条来源重复 3 次 |
| `GET /api/v1/relation/list?limit=10000&offset=0` | 614 ms | 返回全部 7,154 个实体；limit/offset 不被 handler 使用 |
| `POST /api/v1/relation/entities/list`，limit=20 | 707 ms | 已上线，返回 20 条及 next_cursor |
| `POST /api/v1/entity/detail`，宏顺 | 104 ms | 轻量人物信息 |
| `POST /api/v1/entity/detail-full`，宏顺 | 15,420 ms | 重型完整详情 |
| `POST /api/v1/entity/records/list`，宏顺，limit=10 | 15,414 ms | 相关原文分页；前 10 条有重复来源 |

以上是单次真实测量，不代表 P95，也不能仅凭接近 15 秒就断言是某个超时。生产排查账号 user_id=11；宏顺 entity_id=`69735cfc262635859ecceada`，周鹏 entity_id=`69735cf1262635859ecce9c4`。不需要重新触发 AI 识别。

## 已确认原因

1. 插件旧列表把全量索引与联系人备注解析串联。备注解析可能继续翻联系人、私聊列表，阻塞首屏。
2. 插件旧详情用 Promise.all 等完整详情及来源记录，之后还可能重读全量索引和备注。来源翻页也重复读完整详情。
3. relation 返回的是提及行：同一 record_uid 可有多个 start_position/end_position。宏顺首条原文的两个区间为 34–36、40–42。插件把每一行画成一张完整原文卡片，首批缺去重；原有跨页过滤也没有合并一页内部的重复项。
4. 两个重型详情接口本身仍慢；根因尚未定位到具体数据库查询。轻量 detail 快，说明不能简单归因为整个 relation 服务或网络普遍慢。

## 插件本轮处理

- 关系列表先返回已有名称、摘要、类型、计数；联系人备注通过独立 enrichment 后补，不阻塞列表。备注搜索仍覆盖全量身份资料，不缩小为已加载页面。
- 保留已有排序、名称/别名/备注搜索及完整数据覆盖；列表按 50 条分批显示，滚动继续加载。
- 人物详情使用轻量 `/entity/detail`；列表已有 AI 摘要立即可读。原文通过独立 records 请求加载，分区占位、错误、重试互不影响。
- 翻来源页仅请求 records，不再请求完整详情或全量目录。
- 最近浏览的关系详情短期按账号缓存，切换可立即恢复；过期后台更新，切换账号清理。切换人物会终止旧请求，禁止旧响应覆盖当前详情。
- 同一来源按稳定记录标识及容器归并，保留不同提及位置，批内与跨页均处理。不同来源即使文字相同也不合并。只改变展示，不删除生产记录。
- 来源尚未返回时显示真实加载状态；不把未返回误显示为没有来源，不做虚假的进度百分比。

## 为何没有直接用新分页接口替换旧列表

`/relation/entities/list` 已存在且可用，应继续复用；但目前不能无损替换：

- 新接口按最近提及时间 + entity_id 排序；旧列表优先微信导入、人物，再按类型、提及数、最近时间等排序。
- 新请求只含 source_types、entity_types、cursor、limit，没有名称/别名/备注全局搜索。
- 新响应缺总数、各类型总数、AI 摘要、别名、linked_user_id 等旧页面使用的字段。
- 新接口基于来源投影代次，需要验证与旧实体列表的数据覆盖差异，包含手建/历史实体、空来源实体、录音可见性和重建中的行为。

本轮旧索引单次读取约 0.6 秒，先移除备注阻塞即可显著改善首屏；这不等于实现了后端真正分页。后续请扩展新接口契约，再迁移以降低大账号传输和内存负担。不要因迁移无意改变排序或使全局搜索仅命中已加载数据。

## 后端优先排查

代码核对基准：jotmo-relation `origin/master` = `3f37a98`。本次涉及的旧列表、详情、来源查询函数与本地审查版本一致。

1. 给 `gin/compound/entity.go` 的 `GetEntityDetailFull`、`GetEntityRecordsList` 增加分段耗时日志/trace，记录请求 ID、user_id、entity_id、limit/offset、返回条数，不记录原文和令牌。
2. 分别测量 entity、entity_topics、entity_notes、entity_records count/list、core_records 批读、import_records 批读、import_batches、头像补全的耗时。检查 Mongo 连接池等待、服务端选择超时、慢查询、explain 和索引命中。
3. `GetEntityDetailFull` 中主题、笔记、记录及各类计数串行执行；插件并不需要所有这些字段。建议保留轻量详情并补充 ai_summary、linked_user_id，避免为了概述进入重型链路。
4. 两条慢链路都调用 `internal/import_record/models.go:SelectImportRecordsByUids`。其查询包含 user_id 和 core_uid/uid 的 OR 条件。需要核查两条分支索引和批量查询耗时；目前只是共同排查点，尚无日志证明它就是根因。
5. `GetEntityRecordsList` 中若部分正文批读失败，当前可能忽略错误继续返回成功；计数失败也可能退为 0。请返回明确的部分可用/可重试状态，避免空正文被误认为没有内容、分页被错误截断。
6. records 分页当前只按 RecordSendAt 降序，缺少同时间的稳定 ID 排序。请增加稳定次级键，并优先提供游标，降低并发新增/更新导致的跨页重复或漏项。

## 建议来源接口契约

按原始记录分页，每条卡片保留一个稳定 source_id（包含 provider/container/record 的可靠身份），在 mentions 中保留多个出现位置。分别返回 unique_record_total 与 mention_total，避免把“提及次数”当作“原始记录数”。

```json
{
  "records": [{
    "source_id": "opaque-stable-source",
    "record_uid": "original-record",
    "subject_uid": "original-container",
    "content": "原始记录正文",
    "mentions": [
      {"start_position": 34, "end_position": 36, "mention_text": "人物名"},
      {"start_position": 40, "end_position": 42, "mention_text": "人物名"}
    ]
  }],
  "unique_record_total": 2,
  "mention_total": 4,
  "has_more": true,
  "next_cursor": "opaque-cursor"
}
```

去重应在分页前按稳定来源身份聚合，不能只在每页去重后沿用 mention_total 冒充来源总数。所有来源继续执行当前用户权限和可见性校验。不同记录的相同文字不得合并。

## 验收

### 本轮前端实测结果

在更新后的 3102 页面使用真实账号只读验证：

- 列表首次显示 50 条约 541 ms，备注随后补齐；这是单次前端可见时间，不能与接口耗时当作同一性能指标。
- 点击宏顺约 59 ms 即出现标题、已有概述和独立来源加载占位；这不代表来源接口已经完成。
- 首批 30 条提及归并为 27 张原文卡片；继续滚动后累计 51 张，已显示内容保持，未发现重复 key 警告。
- 短期内切换其他人物再返回，约 270 ms 恢复缓存的 27 张卡片。
- 首条原文只显示一次，保留“此原文提及 2 处”；点击定位打开原始快记，时间和正文一致。
- 43 项针对性测试、TypeScript 检查和完整构建通过。未修改后端，未合并 dev/master。

### 后续验收标准

- 人物信息先显示，任何来源慢请求不阻塞标题、概述、已加载列表。
- 同一原文两处提及只占一张卡片；跨页仍只有一张，并保留全部位置。
- A → B 快速切换，A 的迟到响应不覆盖 B；退出/换账号不复用前账号缓存。
- 局部失败不抹掉已加载内容，重试只针对失败区域。
- 真实来源接口分别记录优化前后 P50/P95 和首屏返回量；建议首批记录 P95 控制在 2 秒内，具体指标由团队按生产负载确认。
- 新分页替换之前完成旧排序、全局搜索、类型总数和全量覆盖对照，明确删除/新增/投影重建时的游标处理。
