# 线下录音与聊天上下文关联：第一期后端交接

日期：2026-10-15。状态：产品交互已确认，插件组件及独立交互预览已实现；自动关联、真实共享、正式时间线接入尚未完成。本轮未修改后端。

## 1. 要解决的问题与一期范围

用户在线上提出问题，随后转为口头交流，聊天里缺少实际回答；或先在线下讨论，再在群里发图片、文件，聊天里缺少讨论背景。录音处理完成后，把一次完整线下交流与具体消息建立关联，在聊天的实际发生时间位置展示卡片。

一期同时覆盖私聊、群聊。高置信关联默认仅在录音所有者自己的聊天视图中可见；不确定候选单独待确认；用户预览后才能分享。不会因同群、同名、声纹相似或时间接近就自动向其他人开放录音。

三种起步场景：

1. 18:24 线上问手机号检查引发发送超时，18:30 左右线下回答按需检查和缓存状态。
2. 线上约几分钟后见面，随后转为线下交流。约见信息只是证据之一。
3. 先讨论录音存储口径，再在群里补充测算图片。必须理解附件内容，不能仅匹配“这是之前的测算”。

不要依赖所有说话人都已绑定联系人：只录到用户单方面回答，也可能与某条线上问题高度相关。但“回答了这个问题”不等于“已证实这个联系人在场”。

## 2. 本次前端交付的实际边界

- `src/offline-context.ts`：提议的浏览器展示 DTO、操作 port、来源范围与分享条件。
- `src/client/offline-context/OfflineContextCard.tsx`：可复用卡片、原文展开、来源定位回调、回听回调、候选确认、范围调整、重新关联、分享预览、移除/撤销和结果不明处理。
- `src/client/offline-context/OfflineContextPreview.tsx`：本地演示容器，使用通用示例，无 API 调用、账号数据读取、真实写入或持久化。
- 预览地址：`http://127.0.0.1:3102/?arkme-offline-context-preview=1`。只允许 loopback 主机显式打开。刷新重置示例，不代表真实关联丢失。
- 正常聊天没有注入示例卡片。后端合同落定后，仍需 Host 适配、统一时间线新事件解析、实时通知、来源导航与权限联调；不能把本次交付描述为自动关联已经上线。
- 示例无音频，因此回听禁用；“定位原文”仅演示来源详情。分享演示不会发送消息。
- 目前只能在演示里重选当前对话的消息；跨对话选择器、正式共享撤回和读取权限须随正式后端一起接入。

## 4. 服务分工建议

1. **Audio** 提供可审计的原始片段、时间、speaker 绑定及修订、播放内容标记、转写版本。以事实为准，不能只给全文摘要。
2. **关联处理服务**（建议由 Relation 或现有 AI 编排服务承接，最终 owner 请后端确认）负责候选召回、语义复核、关系去重、纠错与重算。
3. **Chat** 负责个人可见关联、共享快照、目标会话权限及统一时间线展示。消息 seq 不承担回插事件的排序职责。
4. **插件 Host** 负责能力探测、账号/环境/会话隔离、引用签封、API 适配、操作状态核对与版本保护；浏览器只使用 opaque refs。

## 5. 关联流水线

```text
新消息/附件可检索 ─┐
录音片段转写就绪 ─┼→ 有界候选召回 → 语义关系复核 → 来源/身份/可见性校验
原文或身份纠正 ──┘                                    ↓
                                      高置信个人卡片 / 待确认候选 / 不关联
                                                      ↓
                                     用户确认分享 → 冻结快照 → Chat 分发
```

- 双向触发：聊天找前后录音；录音完成找前后聊天。处理延迟不改变发生时间。
- 初始召回窗口可从前后 30 分钟起步；约见表达可扩展到约定时间，跨午夜也要支持。该数值是待评估参数，不是硬判断规则。
- 复用时间轴/转写片段和搜索索引，按账号、时间、会话/联系人候选收窄后再模型判断；避免每条消息重扫全天录音。附件 OCR/视觉摘要按文件内容版本复用。
- 关键词、语义向量、可靠实体、联系人绑定提供多路候选；不要以某个向量距离（例如 0.3）直接决定关联、人物身份或共享权限。
- 输出关系类型：回答问题、线下讨论后的补充、约见后交流、延续讨论；允许“无关”和“证据不足”。每条结论必须引用消息与转写原句，不能只给置信分数。
- 先确定一次完整交流，再选择其中与目标消息相关的连续范围；不跨明显话题切换拼凑答案。整段会议跨很长时间时，可关联多个片段，但保持同一交流的聚合身份。
- 已明确为手机播放的片段排除；unknown 不等于 in_person。环境音/播放判断仍不可靠时降级为候选。
- 不等整天总结或实体识别任务完成。已就绪片段可增量处理，同一关联更新版本，不重复创建卡片。
- 没有录音、没有匹配或仍在处理应有不同状态，不能让用户把“还没产出”理解为“没有线下交流”。

## 6. ASR 错字与身份处理

原始转写与规范化候选分别存储。允许联系人词表、项目词和语音近音辅助召回；涉及关键人名、否定、数字的判断，可对少量原音复核，不要为了匹配聊天改写原文。

分别保存语义关系证据、参与人证据与共享授权。即使开头名字转错，具体问答内容仍可支持个人关联；不能仅因称呼近音就绑定联系人或扩大共享受众。摘要写“讨论建议/提出方案”，没有落实证据不能写“已解决/已完成”。

## 7. 需要保存的数据

以下为逻辑合同建议，字段名和路由请后端确认，当前不代表已有 API。

| 对象 | 必须包含 |
| --- | --- |
| 关联主体 | stable association_id、owner、chat_session_uid、revision、状态、visibility、关系类型、模型/策略版本 |
| 时间 | occurred_start/end、created_at、updated_at、shared_at（可空）、可靠时区/录音时钟依据 |
| 消息证据 | 实际 record/relation 身份、会话、消息版本、发送时间、文本或附件内容摘要来源 |
| 录音证据 | owner、session_id、child_id、item_index、transcript_source、转写版本、字符区间、音频时间范围 |
| 身份/来源证据 | 已确认参与者、speaker/person 当前修订、in_person/playback/unknown、依据及不确定项 |
| 结果 | 标题、要点、证据引用、关联理由、source_state、待确认原因 |
| 用户决策 | 确认、排除原因、改范围、改目标、移除、撤销；决策版本与时间 |
| 共享快照 | 分享人、接收会话/受众规则、实际分享时间、选定正文、原文是否包含、快照版本、撤回状态 |

UI `OfflineContextEntry.id` 和 refs 是账号绑定的不透明展示身份；后端不要把这些 UI refs 当作永久业务主键。原文定位必须校验版本，不能在重转写后用旧字符偏移定位到另一句话。

一个 association 可以对应多条消息、多条连续原文。相同源版本/交流/目标会话的重试必须幂等；范围修订、来源更新保留稳定身份与版本链。不能仅靠摘要文本哈希去重。

## 8. 建议的能力合同和操作

先协商能力版本（例如 `offline_context_v1`），未声明能力时正式界面不启用、不盲调猜测的 API、不用假成功降级。

需要提供以下逻辑操作：

- 查询当前会话的关联候选、状态和有界详情；已确认关联通过统一时间线返回。
- 精确读取消息/原文与按授权回听，源不可用时保留卡片位置并给出明确状态。
- 确认关联；排除 unrelated/playback；移除；撤销；修改源范围；改关联目标。
- 预览分享范围及内容；提交分享；查询分享状态；撤回共享。
- 查询幂等操作 request_id 的状态：applied / not_applied / pending / expired_unknown。不能把查不到关联直接等同于“请求没执行”。

所有变更携带 request_id、expected_revision。账号从认证取得，目标会话/来源权限在服务端验证。请求结果不明时返回可核对状态；不允许前端随意重试写入。过期或冲突时返回最新可读版本，不覆盖其他设备的新修改。

当前 UI port：`change({requestId, entryId, expectedRevision, conversationKey, change})`，其中 change 为 confirm/dismiss/restore/range/relink/share。`reconcile(action)` 必须核对同一个 request_id；pending 时继续禁止重复写入。正式 Host 要持久保存未决请求，切换会话或刷新后继续核对；预览仅内存模拟。

改范围后旧摘要立即标为待重算，不可继续分享不对应新范围的旧摘要。错误关联形成持久排除证据，重跑不能再次自动插入；用户撤销才解除该决策。内容纠错不能顺带修改声纹。

## 9. 统一时间线和实时刷新

建议扩展一个明确的 `offline_context` 来源/事件类型，具体排序位由 Chat 协议统一决定，不挤占现有 interwoven 类型，不伪装正常发送记录。

- 18:30 发生、19:10 才处理完成：个人卡片位于 18:30，创建时间保留 19:10。
- 19:15 才分享：受众可按交流时间阅读卡片，同时知道 19:15 才被分享；通知/投递按分享事件处理，不能伪造 18:30 已收到或已读。
- 现有 messages seq 用于同步和已读。插入个人上下文不增加对端未读、不伪造发送者、不触发对端推送。
- 异步插入使用 source revision/失效通知重新读取当前覆盖窗口，保留滚动锚点。窗口外可提示“补入 N 段线下交流”并提供 around 导航；不能直接把用户拉走。
- initial/older/newer/around/refresh 均须包含该来源；处理 gap、内容不可用、撤回 tombstone、来源退役，服务端稳定总序和客户端缓存版本必须一致。
- 重新识别更新同一关联，用户确认/排除决策优先。重复完成事件、断线重连和跨设备同步不得产生重复卡片。

## 10. 共享与群聊规则

一期先复用已有文字共享思想：标题、要点，可选所选原文；不包含原始音频和片段范围外内容。服务端冻结的分享预览必须与最终发送一致，预览之后来源或受众变化需重新确认。

群成员并不等于线下参与者。只有个人视图的关联推断不会自动开放录音。分享提交时检查目标会话、当前成员资格及发送权限；读时再校验共享规则。新成员能否读历史共享须遵循并明确现有群历史政策，不由模型决定。

共享后不允许“改范围”静默替换对方已经看到的内容；需明确更新版本或撤回后重新分享。个人移除关联与撤回共享分开，前者不删除原始录音，也不自动删除对方的已分享消息。接收者打开共享卡片只能读取授权快照，不获得原录音库权限。

## 11. 首轮验收矩阵

| 用例 | 通过标准 |
| --- | --- |
| 问题后几分钟口头回应 | 找到对应问答，卡片时间正确，原句证据可查 |
| 开头人名错字/对方没出声 | 不因姓名不匹配丢失语义候选，不虚构对方身份 |
| 先讨论、后发测算图片 | 读取附件主题并反向关联，无关图片不匹配 |
| 同时多个会话讨论相近话题 | 不能仅凭关键词选错会话，有歧义进入待确认 |
| 旁边播放短视频 | 明确 playback 不自动关联；unknown 不默认为真人交流 |
| 录音跨文件/午夜/延迟上传 | 完整片段、正确发生时间、不重复卡片 |
| 查看原文/回听 | 精确句子与范围，权限和源版本匹配 |
| 改范围/改目标/排除/撤销 | 摘要重新核对，纠错跨刷新/设备保持，重算不复活排除项 |
| 群聊分享 | 预览接收范围和正文，最终内容一致，未分享对他人不可见 |
| 网络超时/重复点击/重复事件 | 幂等，结果不明可核对，不重复发送 |
| 来源删除/转写更新/成员退出 | 状态明确，失效引用不越权、不定位错误原文 |
| 历史分页和阅读位置 | 补入发生时间位置，刷新不跳动，around 可找回 |

先使用人工标注的正反例评估关联准确率、误插入率、候选确认率、漏关联率、来源定位成功率、处理延迟和成本。自动卡片门槛应由这些样本校准，不能直接用未经校准的模型百分比。

## 12. 建议对接顺序

1. 后端确认 owner、能力版本、DTO、来源锚点及个人可见权限；先返回固定测试数据做合同联调。
2. 插件接入真实统一时间线和来源跳转，完成分页、刷新、读取失败验证。
3. 接入有界语义关联和双向增量触发，先跑人工标注样本，再对真实账号灰度。
4. 接入持久纠错，校准高置信个人卡片门槛。
5. 对接私聊/群聊分享预览、幂等提交、撤回和受众验证。

不需要个人导出的候选 JSON 才能开发本功能；示例仅用于交互，生产关联由各账号授权数据实时或离线计算。不要把某位用户的录音候选当成全站历史回填清单。
