# 统一模型目录、场景执行与积分：后端对接

日期：2026-11-02。接收：华焱（群内名称 Lucis）。本地前端预览已实现，未发布。

2026-11-03 更新：模型来源统一为“即我官方／用户自提供”，百炼属于官方的供应商；场景计费需独立核实。分组、场景范围和计费语义以[最新补充](模型来源两类与场景计费核验-20261103.md)为准。

## 用户要解决的问题

桌面端 DSH、Arko、录音总结/时间轴三处模型选择不一致。用户需要在所有入口看到完整接入目录、准确的名称/版本/渠道、可用和预占积分、计费说明、用量明细与充值入口。已接入模型应始终可查可选；场景不支持时给出明确原因，不能在不同入口静默隐藏。

## 已确认的当前事实

1. DSH 读取公开模型目录；Arkme 托管分组使用 `/api/v1/managed-ai/models/query`。
2. Arko 使用 `/api/v1/agent/model/list`。本次实际账号返回 1 项，名称 `DeepSeek V41 Flash`，route key 为 `managed-ai/deepseek-v4-flash`。
3. 录音使用 `/api/v1/audio-summary/model-config/list`，本次返回 8 项，使用独立 route key。
4. 实际只读汇总取得 DSH 7 项、Arko 1 项、录音 8 项，三处均读取成功。16 是原目录项数量，不能宣称是 16 个去重后的模型。
5. 名称、渠道标识和 route key 不是同一合同；DSH 的 `DeepSeek-V4.1-Flash-1017` 与 Arko 的 `DeepSeek V41 Flash` 不能仅凭近似名称合并或互换路由。当前目录也未提供统一的运行版本字段。
6. 积分查询 `/api/v1/managed-ai/points/query`、套餐查询和充值页面已经存在。此次缺口主要是入口与共享展示。DSH 的 DeepSeek Account 渠道与 Arkme 托管渠道需要分别说明计费账户。
7. 本地服务端源中的用户态托管目录已定义 `catalog_release_id / offering_revision_id / supplier_code`。插件已补读这些字段并在提供时显示；这部分不应重新建设。它们是目录/配置版本，不等于模型实际运行版本。请先确认当前部署返回情况及现有统一目录合同。

这些是代码和实际账号接口的读取结果，没有新增收费测试任务或支付订单。

## 前端已完成

- 三处使用同一个模型面板，包含搜索、完整汇总列表、选择、渠道、思考强度、计费说明、生效范围、积分和预占、用量明细与充值。
- 录音去掉弹窗内再次打开模型下拉的层级；输入框旁也可发现积分和充值入口。
- 新增插件 Host 只读操作 `models.directory`，聚合现有 DSH、Arko、录音目录；这不是已部署的后端统一目录接口。
- 同一渲染器共享账号绑定的目录和积分状态，合并并发读取；切换账号清空旧状态，迟到响应不覆盖新账号。
- 保留已验证的原场景执行路径和生效范围：DSH 当前对话、Arko 后续新任务、录音总结与时间轴。
- 对缺少当前场景执行绑定的模型，仍允许在面板中选择查看，标为“支持待确认”；点击应用时解释路由未接通，不猜测跨场景 route key，不静默改成其他模型。
- 未提供的具体版本、报价或任务费用估算明确显示待确认；可用积分为正不等于保证本任务费用充足。

## 需要确认或补齐的合同

优先确认是否已有可面向当前用户读取的统一目录。若已有，请给出现有真实接口和脱敏响应，避免再建重复目录。若没有，建议返回下列语义；字段名和路由均为待确认提案。

| 内容 | 所需语义 |
| --- | --- |
| 模型身份 | 稳定 canonical model ID；模型族、具体版本、展示名、是否动态别名、实际解析版本 |
| 渠道身份 | 供应商与渠道独立字段；同模型不同渠道的关系、可选路由及计费归属 |
| 场景能力 | DSH、Arko、录音总结、录音时间轴等场景分别给出 supported / unsupported / unknown，以及原因 |
| 执行绑定 | 每个支持场景的真实执行标识；旧 route key / public model code 的显式映射，不能由前端根据名称拼接 |
| 模型能力 | 图片、工具调用、结构化输出、思考强度等有版本的能力说明；选模型后由执行端最终校验 |
| 生命周期 | 当前可选、已下线、替代版本和原因；目录 revision、更新时间、失效刷新方式与完整性 |
| 积分报价 | 以字符串传输的精确积分价格；输入、缓存输入、输出与工具/其他服务费；明确每千或每百万 Token 单位 |
| 计费账户 | Arkme 积分、外部渠道账户或其他结算方式；不能把外部账户费用展示成消耗 Arkme 积分 |

目录应该覆盖系统当前接入的全部模型，按场景返回支持状态，而不是让三个业务接口各自裁剪出不同名单。权限、下线和场景不支持需要有明确状态，不能被一个笼统“不可用”混淆。

## 任务费用与积分不足

现有余额查询不能独立回答“这次工作够不够”。请确认有无启动前的服务端费用/准入校验：

- 绑定账号、场景、准确模型/路由、输入规模、允许的输出及工具预算。
- 明确可启动、积分不足、报价待确认、暂不可用；费用区间、预占额度、估算时间与有效期须区分。
- 任务 idempotency key 与预占标识绑定；重试不重复扣费，取消/失败后的释放规则明确。
- 长任务中途不足时的续费/继续语义明确，保持用户草稿和既有结果；不能静默降级模型或隐式充值。
- 充值完成后刷新可用与预占积分；实际扣费以服务端账本为准，不能仅凭支付页面关闭视为到账。

没有可靠估算时，前端显示“费用待确认”，不生成虚假的预计费用或“积分足够”保证。

## 验收要求

1. 同一账号从三处打开面板，拿到同一份完整目录与 revision；差异只体现在当前选择、场景状态和生效范围。
2. 每个已接入模型都能在三处找到；不支持的场景说明原因，支持的场景真实执行用户选中的版本与渠道。
3. 同名不同渠道、别名更新和下线后，实际执行回执可追溯到精确模型与版本；旧任务续跑遵循明确规则。
4. 各模型显示正确的积分报价和计费账户；余额不足、网络故障、预占释放与充值到账可实际验证。
5. 目录部分失败、账号切换、权限变化与迟到响应不能显示他人余额或恢复过期执行绑定。
6. 请提供实际合同、部署环境、脱敏样例及可联调任务。仅前端出现选项，不代表跨场景执行、统一计费或具体版本识别已接通。
