# 双向团队私信后端交接

日期：2026-10-25。范围：Arkme 插件第一阶段，团队成员主动联系外部用户。

现在外部用户可通过团队入口发起会话，团队成员共同查看、回复。本次补齐反向入口：成员在群里看到反馈后，从该用户头像选择「以团队联系」，后续沟通进入团队通道，其他有权限的同事可以接续处理。用户原有个人私聊保持独立，不自动分享其历史。

## 本次前端已完成及待接通边界

| 位置 | 已完成交互 |
| --- | --- |
| 私聊、群聊的普通用户头像卡片 | 并列「发起私聊」「以团队联系」；本人不出现团队联系操作 |
| 联系人资料 | 增加「以团队联系」，保留个人发消息、语音和视频操作 |
| 团队会话目录右上角 | 增加「联系用户」；进入某个团队后自动带入该团队 |
| 共用选择弹窗 | 加载真实团队；只有一个团队时默认选中，多个团队时明确选择；从联系人分页选择，或用即我号、手机号精确查找 |
| 发起结果 | 预留 ready 返回后的现有团队会话导航、列表刷新；不另建一套聊天 UI |

弹窗明确显示「以某团队身份发给某用户」及「本团队有权限的成员可共同查看和回复；个人私聊历史不会自动共享」。个人备注仅供当前操作者识别用户，不作为授权参数，也不传给外部用户或其他成员。

本次入口在主窗口内提供。独立弹出的个人/群聊窗口固定绑定原会话，目前没有向主窗口移交团队会话的导航协议，因此不显示新入口；后续客户端需支持带团队会话目标激活主窗口，再复用本弹窗，不能在固定窗口里悄悄切成另一会话。

**当前不能真实创建主动团队私信。** 插件新增的 `team.app.outbound.open` 目前校验账号、团队引用及当前成员资格，然后返回 `backend_pending`。前端显示「后端接口开发中，开发完成后此功能完整可用。」，保留当前弹窗中的选择，不创建个人私聊，不制造团队会话，不发送消息。关闭弹窗后不承诺恢复未提交选择。

现有 `team.app.open` 调用 `/api/v1/team/conversations/open`，请求只有 `public_ref`，用于外部用户经团队公开入口打开会话；不能用它冒充团队成员主动指定用户的接口。新增上游地址以下仅为建议，**尚未部署、当前代码也未调用**。

## 实施顺序

1. 双向团队私信：本文件描述的第一阶段；所有入口共用真实会话及权限模型。
2. 团队加入群聊：团队作为独立群参与者，明确群成员可见身份、团队内访问权限、历史范围、退出规则。
3. 群内个人与团队身份选择及群聊互动映射：复用「发给自己」的身份选择交互，但群内先仅提供本人和有权限代表的团队；群内 @团队、团队回复映射到团队通道时保留群来源和权限。
4. 之后再抽象统一身份模型。「发给自己」即使选择工作或团队身份，也仍是个人私密内容；不得因为身份归属而让团队成员可读。

阶段二、三的权限与身份协议应一起设计，发布顺序仍在第一阶段之后。本次不实现团队入群、群内身份选择、私聊历史自动迁移。

## 已落地的插件内边界

入口、选择和导航分别位于：

- `src/client/ArkmeChatMemberActions.tsx`、`ArkmeSidebar.tsx`：头像卡片及当前会话成员引用。
- `src/client/redesign/contacts/ContactProfileDetail.tsx`：联系人资料。
- `src/client/TeamConversationDirectory.tsx`：团队目录入口。
- `src/client/TeamOutboundDialog.tsx`：唯一的选择、提交、等待后端提示及 ready 导航界面。
- `src/client/team-outbound.ts`：按账号传递发起意图，不写入聊天数据。
- `src/team-outbound-contract.ts`：输入目标及结果联合类型。
- `src/services/team-app-service.ts`：`team.app.outbound.open` 的当前占位边界，后续接上真实上游。

前端向 Host 请求：

```ts
{
  operation: 'team.app.outbound.open',
  params: {
    expectedAccountKey: 'prod:当前登录用户',
    teamRef: '账号绑定的不透明团队引用',
    requestUid: '同一次尝试及重试共用的 UUID',
    recipient:
      | { kind: 'chat-member', sourceRef: '会话引用', memberRef: '成员引用' }
      | { kind: 'directory-contact', contactRef: '联系人目录引用' }
      | { kind: 'contact-lookup', contactRef: '精确查找结果引用' }
  }
}
```

以上是类型示意，不是可直接提交的 JSON。三类引用来自不同的签发上下文，Host 必须通过原签发服务校验、解封并解析真实用户，不能互换或从昵称、备注推断用户。当前占位实现仅校验目标参数形状，不解析目标、不执行任何目标用户写操作；真实接口接入前必须补上解析和访问校验。前端不接收或自行拼装内部用户 ID、团队 ID。

```ts
type TeamOutboundOpenResult =
  | { state: 'backend_pending' }
  | { state: 'ready'; conversation: TeamConversation }
```

ready 由 Host 投影真实上游会话，至少沿用 `ref`、`key`、`side: 'team'`、`channel`、`visitor`、序列及未读字段。`channel.jotmoId` 必须与选择的团队匹配。引用可轮换，不能用加密引用字符串判断是否同一团队。

当前 UI 已处理重复点击、账号变化、关闭弹窗后晚到结果、团队加载重试、团队资格失效、联系人分页及旧搜索结果覆盖问题。同一弹窗内重试保留 `requestUid`；后端接入时需补上 Host 持久化恢复或依靠团队与用户唯一约束，覆盖进程退出后的结果不确定场景。

## 后端需要提供的能力

### 主动联系权限及目标解析

团队列表应返回明确的 `can_start_external_conversation` 及不可用原因；是否允许普通成员发起由服务端权限决定，不应由前端把 owner、admin 或 member 硬编码为唯一允许角色。

请求需检查当前登录账号、团队成员资格、发起权限、通道状态、目标账号存在及接收规则。群聊中的目标必须校验操作者具有访问该群及该成员身份的权限；联系人与精确查找结果同理。被拉黑、目标注销、无权访问、通道停用等情况返回明确业务码，不返回其他用户私有资料。

建议第一阶段仅允许团队联系团队外的已注册个人用户。本人、团队账号、当前团队内部成员不得混入外部会话；如后续业务允许内部成员作为外部客户，应单独约定身份和权限，不能默认绕过限制。

手机号仅用于用户显式点击「精确查找」，不做全量上传匹配；复用已有查找限流与隐私规则。不能因有团队权限而绕过用户的消息接收、拉黑或频率限制。

### 幂等打开与同一会话复用

建议新增 `POST /api/v1/team/conversations/open-by-member`，或者在经双方确认的原接口中增加明确的发起模式。上游请求由 Host 解析后包含：

```json
{
  "team_id": "真实团队 ID",
  "external_user_id": "校验后的真实目标用户 ID",
  "request_uid": "发起尝试 UUID"
}
```

操作者来自登录态，不能信任客户端提交的 actor。服务端对 `(team_id, external_user_id)` 保证唯一：外部先联系、成员先联系、多个同事并发发起，都必须返回同一个逻辑会话；个人私聊仍是另一条独立会话。

`request_uid` 与操作者、团队、目标绑定。同一请求重复提交返回同一结果，参数不同则冲突。会话隐藏、移除或历史归档不应导致重复创建；再次联系按现有会话恢复规则处理。

只打开窗口不发送消息、不增加未读、不通知外部用户。无首条消息的会话不能在外部收件箱制造空会话；服务端可使用待激活会话，在首条消息成功提交后再激活并发布目录事件。若实现采用其他机制，需要同样保证该用户体验。

### 发送者及双方呈现

第一条消息仍使用现有团队发送、附件、幂等队列与状态流程。团队端显示外部用户；外部端显示团队名称、头像及团队标识，使用户明确是在和团队沟通。

每条团队发出的消息保留「代表的团队」和「实际操作成员」两个身份。团队内部可追溯实际回复者；外部端沿用已有团队通道的成员署名规则，不得显示成个人私聊。消息的编辑、撤回、删除、发送信息和审计都按现有团队权限校验。

任何个人私聊历史、私人备注或私人快记都不自动迁移到团队会话。本阶段没有「将既有私聊转为团队会话」操作。

### 同步与生命周期

首条消息成功后，更新双方的会话目录、预览、最后活动时间、未读数量，并向有权限的团队成员设备推送变化。复用现有团队会话和消息 ID；重试、断线重连不得出现重复卡片、重复消息或重复提醒。

内部已读按成员分别记录；外部已读状态独立记录，保持现有团队通道的查看方式。点击打开空窗口不能标记尚未加载的消息为已读。

成员退出或被移除、权限变化、通道停用时，服务端在读取及真正发送时再次校验，不能仅在打开窗口时校验。撤销访问后本地视图和缓存遵循现有团队权限失效流程，历史审计保留但不再允许继续查看和发送。

推荐业务码：`not_team_member`、`outreach_forbidden`、`channel_disabled`、`recipient_unavailable`、`recipient_is_self`、`recipient_is_team_member`、`recipient_blocked`、`rate_limited`、`request_conflict`。网络失败与业务拒绝必须区分，并给出是否可重试。

## 接口接入和验收

后端给出确切路径、请求/响应样例、能力字段、幂等语义及错误码后：Host 接上三类目标引用解析和真实 open 请求，投影成上述 ready 结果；前端共用弹窗和现有团队消息页继续使用，无需重新设计入口。

验收需覆盖：

1. 群成员头像、联系人资料、空团队目录三个入口均可发起；多团队不选错身份。
2. 普通成员和管理者按真实权限得到可发起或明确拒绝结果。
3. 选择但不发送时外部无新通知；首条消息后外部看到团队，有权限的同事都能看到并接续回复。
4. 先外部发起再内部打开、先内部发起再外部打开、两名同事同时发起，均只有一条团队会话。
5. 双击、超时重试、关窗重开、客户端退出后重试不重复建会话或发送；不确定结果能够恢复。
6. 个人私聊及其历史保持私密；成员看到自己的备注，其他人不会收到该备注。
7. 退出团队、切换账号、通道关闭、被拉黑或收件规则变化后，不发生越权查看或发送。
8. 跨设备目录、未读、预览、外部及内部已读同步；现有附件、多选、延展、详情操作回归。

当前自动化只验证已落地的 UI、Host 占位与结果分支；真实创建、双向同步及发送需后端完成后使用授权测试账号联合验收。
