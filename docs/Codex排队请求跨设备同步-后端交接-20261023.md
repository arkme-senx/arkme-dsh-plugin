# Codex 排队请求跨设备同步 · 后端交接

日期：2026-10-23。状态：插件已按下述新增协议实现能力探测、独立队列上传/确认、云端读取和展示；**新增协议仍需后端确认和实现，不代表生产已接通**。本次只同步查看排队状态，不增加远程派发、修改或取消任务的能力。

## 要解决的问题

同一用户在来源电脑的 Codex 中追加后续请求后，即使当前回答未结束，登录即我的其他设备也应看到该对话的排队数量、顺序和文字。输入框中尚未提交的草稿、AI 自行列出的计划步骤不属于排队请求。

当前插件已读取可信接入会话对应的 `queue_1.sqlite` / 旧版桌面队列，但旧云端协议只有对话元数据和已发生的提问/回答；没有队列快照。因此历史界面的“暂仅在来源电脑可见”是缺少云端链路，并非远程派发未连接导致。

**本版队列仅本人账号跨设备可见，团队成员不可见他人的排队请求。** 图片、附件仅发送数量，不上传路径、图片、附件内容。继续使用现有账号、团队、来源和任务授权，不新增新的云端产品。

## 能力声明（启用开关）

在现有 `POST /api/v1/team-codex/connection/status` 返回字段中增加：

```json
{
  "owner_ref": "11",
  "has_connected_codex": true,
  "first_connected_at": 1792760000000,
  "capabilities": {
    "codex_queue_snapshot": { "version": 1, "visibility": "owner" }
  }
}
```

`tasks/list` 也建议返回相同的 `capabilities`，供只读设备提示服务能力。仅当 `version=1` 且 `visibility=owner` 时插件才上传队列。缺失、版本不匹配或权限为 team 时不上传未知字段，继续使用原有聊天同步。探测结果缓存最多五分钟，切换账号立即清除。

**只有服务端已完成 owner-only 存储、读过滤和独立 ACK 后才能开启能力声明。** 不能先返回支持而忽略队列字段。

## 上传：扩展现有 sync，不混入正文事件

继续使用 `POST /api/v1/team-codex/sync`、现有 JWT 和 `expected_owner_ref/team_ref/source_id/source_name/tasks`。队列与正文使用不同批次；队列批次中每个 task 仍带现有元数据和元数据 `version`，`events` 为空，额外带 `queue_snapshot` **或** `queue_heartbeat`。

```json
{
  "expected_owner_ref": "11",
  "team_ref": "101",
  "source_id": "现有来源 UUID",
  "source_name": "来源电脑",
  "tasks": [{
    "task_id": "现有任务 UUID",
    "version": 3,
    "project_key": "现有项目 key",
    "project_name": "现有项目名",
    "task_title": "对话标题",
    "branch": "",
    "events": [],
    "queue_snapshot": {
      "schema_version": 1,
      "visibility": "owner",
      "version": 8,
      "availability": "ready",
      "reason": "none",
      "observed_at": 1792760010000,
      "changed_at": 1792760010000,
      "source_at": 1792760009000,
      "items": [{
        "request_id": "任务内稳定的 SHA-256 标识",
        "text": "继续处理第二项",
        "created_at": 1792760008000,
        "delivery": "queue",
        "state": "queued",
        "paused": false,
        "attachment_count": 0,
        "truncated": false
      }]
    }
  }]
}
```

- 顶层 task `version` 是原有元数据版本；`queue_snapshot.version` 是独立的队列版本，两者不能混用。
- 作用域：已验证的 `owner + team + source + task`。后端必须核验 task 属于该 source、来源属于当前账号且允许上传到目标团队。
- `items` 数组顺序就是来源顺序，不能按文字、时间或 ID 重新排序；同文不同 `request_id` 是不同请求。
- `request_id` 是插件对 `cloud_task_id + 本地请求ID` 的哈希，不是可用于调度 Codex 的原始 ID。
- `availability`：`ready | partial | unavailable | stale | paused`。
- `reason`：`none | unavailable | unsupported | wrong-home | excluded | paused | ambiguous-owner`；`ready` 必须是 `none`。
- `delivery`：`queue | send-now`；`state`：`queued | pending | sending | unknown`。
- 时间均为 Unix 毫秒、安全非负整数；`changed_at <= observed_at`；`source_at` 可为 null。观察时间来自来源电脑，不能以服务端收到时间覆盖、伪装来源仍在线。
- 最多 200 项，每项文字最多 4096 UTF-8 字节；单批最多 50 个任务，整个 JSON 最多 1 MiB。插件会去除已知密钥、图片/附件本地引用，不发送原始路径或工具日志。
- **`ready + items:[]` 才表示确认空队列。** 字段缺失表示本次未提供，不能清空。失败/partial 不是删除证据，前端保留上次可读的片段并提示不完整。
- 同版本同内容重试应幂等；同版本不同内容返回 conflict；更旧版本返回 stale，绝不覆盖。新版本代表整个当前状态；不要把旧版本新增的项目重新并入。
- 不用队列心跳更新 `latest_at`、正文事件数、最后回答时间或任务排序。队列更新与正文时间独立。

### 不变时的轻量心跳

来源内容未改变时，不反复上传正文；每个任务最多每 60 秒发送一次：

```json
{ "queue_heartbeat": { "version": 8, "observed_at": 1792760070000 } }
```

它与 `queue_snapshot` 互斥，处于同一个 task 层级。只有服务端确实持有该版本时，才单调更新 observed_at 并确认。版本不存在时返回 `snapshot_required`；插件将重传完整当前版本。旧版本心跳不得更新新版本。禁止用定时服务端时间把离线来源显示为在线。

### 必须独立确认队列

```json
{
  "owner_ref": "11",
  "task_results": [],
  "event_results": [],
  "queue_results": [{
    "task_id": "现有任务 UUID",
    "version": 8,
    "observed_at": 1792760010000,
    "status": "saved"
  }]
}
```

- ACK 的 task、version、observed_at 必须对应请求中该项。
- `saved | unchanged`：队列已持久化，可确认；`unchanged` 适用于幂等重试及心跳。
- `snapshot_required`：仅用于心跳，要求重传完整版本。
- `stale | conflict`：附 `error_code`，插件保留记录并阻断自动覆盖。
- `rejected`：附 `retryable`、`error_code`；可重试失败使用独立退避，不阻塞后续普通聊天同步。
- 缺少、重复、错误归属/版本的 ACK 均不能被当成保存成功。原有 task/event ACK 不能代替 queue ACK。
- 后端需将快照提交数据库后再确认，不能只入内存队列即返回 saved。接收更新和版本检查须原子执行。

## 读取：扩展现有 tasks/list

`POST /api/v1/team-codex/tasks/list` 保持现有分页及权限过滤，在所属账号自己的 task 行里返回上述完整 `queue_snapshot`；心跳已经体现在 `observed_at` 中。无需请求正文 `events/list` 才能获知队列数量。

- 同账号在其他电脑没有安装采集 Hook、没有本地派发连接，也应能读取。
- 对其他团队成员的任务行，**服务端必须省略 queue_snapshot**，不能只依赖前端隐藏；不能通过改 owner_ref/member_ref/source_id/task_id 读到别人的队列。队列不得进入团队广播、搜索结果、分享/导出正文或其他未授权出口。
- 插件还会再次检查已鉴权任务行的 owner，拒绝呈现他人队列。
- 撤销团队权限、任务删除、来源失去授权时按现有 ACL 拒绝/移除；不能复用队列缓存绕过授权。
- 插件按账号、团队、来源、任务保存最后已验证快照；暂时没有队列字段或数据损坏时显示旧内容并标为待更新，不显示假零。低版本响应不会恢复已移出的请求。
- 观察时间超过 90 秒，界面显示“上次队列”和更新时间；这是来源状态过期，不代表已经没有任务。后台成功重读后恢复。

## 前端体验与触发机制

沿用 DSH 风格的底部队列：一条直接显示，多条默认折叠为数量，展开显示顺序、文字和必要状态。云端读到的内容是只读视图，不允许用该列表远程发送/取消。

采集仍沿用现有 Hook 文件事件及原有本地兜底检查；本次不增加新的高频全量扫描。队列内容、顺序、可读状态变化后，会提前触发既有云端同步泵；进程运行期间的重试按退避执行。只有观察时间变化时不创建新内容版本，最多一分钟发一次轻量心跳。接收设备沿用已有活动页刷新机制，隐藏页面停止刷新，不另建五秒全量扫盘。

## 交付与联调边界

插件涉及文件：

- `src/team-codex-queue-wire.ts`：协议白名单与校验。
- `src/team-codex-queue-cloud.ts`：独立版本/ACK、持久待发送状态、最后已知云端队列。
- `src/team-codex-cloud.ts`：能力门控、现有 sync/tasks/list 对接、账号隔离与独立退避。
- `src/team-codex-machine-journal.ts`：队列变化提前触发同步。
- `CodexQueueDock.tsx` / `personal-codex-state.ts`：本人跨设备只读显示及过期/离线反馈。

本地自动化用两个独立数据库模拟来源端/读取端，验证新增、编辑、调序、清空、重启恢复、幂等 ACK、错误/缺失 ACK、旧版本、心跳、断网、权限/账号切换和他人隔离。**这些是协议模拟测试，不能替代后端上线后的真实双设备验收。**

后端完成后最少验收：

1. A 电脑加入 2 条请求，当前回答尚未结束；B 设备同账号看到 2 条及正确顺序。
2. A 编辑、调序、移出，再清空；B 收到新版本，旧响应重放不能把已移出的请求恢复。
3. 断开 A 网络，B 保留旧快照并超时提示；A 重启恢复后自动更新，无重复新增。
4. A 暂时读不到 Codex 队列，不得上传“确认空队列”；恢复读取后才替换。
5. C 用另一个团队成员账号读取同一个任务，响应里不能出现队列内容。
6. 撤销团队权限/切换账号，B 不再展示旧账号队列；再次合法授权后按正常链路读取。
7. 服务端丢失队列快照，心跳返回 snapshot_required，A 重传完整版本。

当前仍沿用既有 `arkme_cn` 团队试用范围；本次没有扩大所有团队的云端授权。协议支持和来源采集都接通后，才能承诺所有已支持的即我客户端跨设备查看。移动端若还未消费该字段，也需按此协议接入；本次交付仅包含桌面插件。
