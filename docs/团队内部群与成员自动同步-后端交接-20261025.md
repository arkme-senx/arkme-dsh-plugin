# 团队内部群与成员自动同步：后端交接

日期：2026-10-25。与 [双向团队私信](./双向团队私信-后端交接-20261025.md)、[团队入群与发言身份](./团队入群与发言身份-后端交接-20261025.md) 一起实施。

## 1. 产品定义

| 场景 | 成员关系 | 输入身份 |
| --- | --- | --- |
| 普通群 | 手动维护个人／Bot 成员 | 本人在团队中即可选本人或代表所属团队，不要求团队先入群；无团队不显示选择器 |
| 团队内部群 | 一个群明确绑定一个团队；人员随团队名单增减 | 本人发言，没有个人／团队切换 |
| 团队参与的普通群 | 团队作为一个主体入群，授权员工代理参与 | 仅一个可用身份时固定；同时有个人和团队资格才可选 |

一个团队可有多个内部群；一个内部群只能绑定一个团队。不能因现有群成员恰好都是同事、群名相同而自动关联。

团队内部群和外部团队私信、团队参与的群仍在同一个团队会话列表中，置顶优先，其余按最新消息排序；不加用户／群聊分类 tab。内部群也可从普通对话列表访问，同一消息只有一份事实，不重复计未读、发通知。

## 2. 当前已实现的前端范围

- 联系人 → 团队 → 团队功能 → **团队内部群**：读取真实团队、填写群名、检查创建条件。
- 普通群右上角 … → 群管理 → **关联为团队内部群**：群主打开，选择自己管理的团队，查看关联影响。
- 页面明确说明成员随团队自动增减、按本人身份发言；现有群需先预览成员变化和历史可见范围，再确认。
- 现阶段真实后端尚未提供创建、关联、影响预览、自动同步。点击只返回“后端接口开发中，开发完成后此功能完整可用。”不创建群、不增加／移除任何人、不假装已关联。不调用普通群接口拼装这种操作。
- 身份规则已按后续产品决定更新：普通群读取本人真实团队，存在有效团队就显示紧凑“头像＋我”入口；团队未入群也可作为代表身份候选。当前选择团队仅打开身份预览和开发中提示，不实际切换发送。已确认是内部群时仍隐藏选择器；当前后端尚无真实内部群绑定，Host 返回 unknown，不从群名或成员名单猜测绑定。见 [个人代表团队发言与团队公开名片](./个人代表团队发言与团队公开名片-后端交接-20261025.md)。
- 账号／目标切换取消旧请求，失败保留表单并可重试；未变更请求复用 requestUid，改表单后换新 UID。

当前插件 Host 操作（不是已部署云端 API）：

```text
team.app.internal-group.prepare
  expectedAccountKey
  teamRef                   当前账号签名引用
  requestUid
  mode: create | link
  name                      create 时必填，去首尾空白后 1–120 字
  sourceRef                 link 时必填，当前账号的 group_chat 引用
→ {state: backend_pending}
```

Host 校验账号、团队签名引用、当前团队成员资格与 owner/admin 角色，关联时校验群引用类型。目前没有确认群管理权、群绑定状态、预览差异或成功创建的能力，pending 不代表这些条件已经通过。云端接入时仍须重新校验全部权限；前端 disabled 不能作为权限控制。

## 3. 后端必须提供的闭环

具体 HTTP 路径由后端确定，以下是建议语义，未冒充现有接口。

| 能力 | 必要输入 | 返回与约束 |
| --- | --- | --- |
| 群团队上下文 | group uid、认证用户 | membership_policy、bound_team、binding_revision、可管理操作、个人发送资格、团队代理资格及版本 |
| 创建预览 | team ref、群名、request uid | 真实成员范围、人数、历史可见策略、能力及拒绝原因、短期 preview token |
| 关联预览 | 原 group ref、team ref、request uid | 当前成员与团队名单差异，新增、移出、保留的个人及 Bot，历史范围、双方权限、短期 preview token |
| 确认创建／关联 | preview token、确认内容、request uid | 原子化绑定、稳定 group/binding id、版本、成员同步进度；重复请求返回同一结果 |
| 状态查询 | request uid／binding ref | pending / complete / failed；未知结果可查询，不重复建群 |
| 名单变化事件 | team id、membership revision、事件 id | 服务端持久化消费，增删成员、撤权、补偿；乱序去重和失败重试 |
| 混合团队会话列表 | team ref、cursor | team_direct / team_group / team_internal、统一稳定会话键、消息时间、未读、可见范围 |

创建和关联都要求团队 owner/admin；关联第一版同时要求原群群主。服务端每次提交重新鉴权并对照预览版本，不能信任客户端提交的名单、actor id、名称或 role。需要更细粒度权限时扩展 capability，不放宽为“在团队中即可”。

预览 token 绑定账号、团队、群、名单版本、原群版本、群名、历史策略与有效期。预览后人员或权限变化，确认应返回 preview_stale 并重新展示差异，不执行旧名单。相同 requestUid 携带不同参数应冲突，不成为第二次操作。

## 4. 成员和历史规则

- 新建内部群：服务端以团队当前有效人员名单创建，正常情况下人类成员集合一致。
- 关联旧群：明确列出新同事、原群中的非团队成员、保留成员。只有用户确认具体差异后才能移出原群成员；不要静默踢人。
- Bot 不属于团队人员名单。已有 Bot 在预览中单独列出，默认保留，沿用群权限；不因团队人员变更被误删。后续添加 Bot 独立鉴权。
- 新同事默认只能查看本次入群后的消息；关联时已有成员保持原有合法历史范围。若产品需要向新同事开放更早历史，必须作为显式策略列入预览和确认，第一版不要隐式开放。
- 离开／被移出团队后立即失去群的在线读取、发送、搜索、统计、导出、附件及分享原文访问权。历史消息保留实际发送者；不是删除其旧消息。
- 离开再加入生成新成员版本和新的历史起点，不复活旧权限。设备上已缓存的内容无法保证物理收回，但退出后应停止展示与新请求，清理授权缓存。
- 内部群人员不再提供独立手工加人／移出；入口解释“成员由团队管理”并导向团队成员页。免打扰、隐藏对话不等于退出团队或移出群。
- 第一版不开放自行退出内部群、换绑另一团队或解除绑定。团队解散后冻结／归档其内部群，不自动变成可继续访问的普通群；保留内容策略需后台统一处理。
- 群创建者离开团队时，由服务端维护管理角色，不让孤立的旧群主权限绕过团队撤权。内部群管理权限跟随团队 owner/admin。

## 5. 自动同步与一致性

名单同步必须在服务端完成，与是否打开客户端无关；禁止前端轮询后逐个调用 members/add/remove。推荐事件驱动＋可靠队列＋低频对账恢复，事件有唯一 id 和单调版本，任务可重试，完成后有进度／失败状态供查看。

关联提交和权威绑定必须原子生效。即使成员投影尚在更新，读取／发送权限也必须使用当前团队名册和绑定规则检查；不能让同步队列延迟造成已离职成员继续访问。前端收到成员或权限变更事件后刷新缓存，不清空正在阅读的合法消息。

普通入口与团队入口使用同一 canonical group uid；入口上下文可以不同，但不是创建两个群、重复存消息。混合列表、分页、未读、置顶与同一设备通知需要按稳定键去重，不因群资料更新而把旧消息排到最前。

账号切换、团队移除、授权收回时撤销订阅、签名引用与图片／文件访问缓存。所有排队发送保留原身份，服务端拒绝失效授权，不能自动换个人身份重发。

## 6. 输入框身份资格投影

```text
state: ready | backend_pending
membershipPolicy: independent | team_roster
personalCanSend: boolean
teams: [{jotmoId, membershipState: active | pending | removed, canSend}]
```

这是建议云端上下文，不是已部署接口。插件当前使用 `TeamGroupContext`，写入状态仍为 backend_pending；list-mine 提供真实团队候选，不提供群绑定或团队代理访问权限。后端接入时由真实群上下文返回绑定关系与发送资格。

- `team_roster`：按本人身份发送，不显示选择器。
- `independent`：本人已入群且是有效团队成员，即可代表该团队，不以团队入群为前提；没有团队时只有个人身份，不显示选择器。只有团队正式入群后授权的代理访问资格、没有个人群资格时，固定团队身份，不出现可用的个人选项。
- 有至少 2 个不同的真实可用身份才显示紧凑选择器。待审批／被移除／不可发送的团队不参与计数，同一团队不能重复计数。
- 切换身份保存独立草稿；每条消息显示实际操作者头像、名称，代表团队时另有团队标识。内部群不凭空加对外代理身份。
- 0 个有效身份时禁止发送并说明原因。已选身份失效时保留草稿并让用户处理，不默默切换。

## 7. 联调与验收顺序

1. 先双向团队私信完成可用闭环。
2. 个人群内代表团队发言、公开名片及联系团队，闭环验证真实操作者、团队成员资格和发送身份；不依赖团队正式入群。
3. 内部群的预览、创建／关联、名单事件与所有读取路径撤权；联调新建群和一个受控旧群。
4. 团队作为主体加入普通群，完成代理访问、消息、历史范围和统一列表。
5. 最后做群内 @团队／回复的来源引用归集。

验收覆盖：团队增删人与群创建并发、预览过期、重复确认、服务重启、离线设备、乱序事件、同步失败恢复、团队解散、旧群非同事移除的明确确认、Bot 保留、新成员历史边界、链接／附件／搜索越权、账号切换、仅一个身份不出现选择器、内部群无身份菜单、多入口未读不重复。

前端目前只能验证入口、资格显示条件与 pending 边界。自动成员同步、创建成功、跨设备结果和真实权限撤销需要后端完成后联合验收。
