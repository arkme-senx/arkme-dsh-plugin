# 安排列表与已删除来源：后端交接

日期：2026-10-25。范围为安排模块列表、详情和删除后访问；前端采用分类 → 列表 → 详情。本文不代表下述缺口已经部署。

## 当前已使用的能力

- 今天、最近7天：`/api/v1/arrangements/list` 分别请求 `status=1/2`，传入 `due_start_at/due_end_at`（含两端，Unix 毫秒）。最近7天为用户本地今天起7个自然日，截止第8天零点前1毫秒。依据安排时间，不能改用创建/提醒时间。
- 全部安排：`status=1/2` 分页读取未完成安排；已完成单独 `status=3`。每页50条，保留已加载内容，不能扫描全部历史才返回。
- 已删除：既有列表支持 `status=4`；Host 新增独立 `arrangements.deleted.list/detail`，只允许当前账号读取，经 UID、status=4 校验后投影为只读数据。原 `arrangements.list` 的状态合同没有放宽。
- 完成/撤销完成继续调用 `/complete`、`/cancel-complete`，回读实际 owner 状态确认成功后才播放完成提示音。提醒继续使用已有开关能力。
- 列表时间与说明、详情来源按现有合同读取。敏感 owner UID 不下发客户端，以账号绑定的 opaque ref 访问。

## 缺口1：已删除安排恢复

目前本地后端路由含软删除，没有公开恢复操作。前端因此没有可执行的恢复按钮。

请提供正式恢复合同，至少包含：

1. 当前登录账号 owner 校验，按 arrangement UID 寻址；只恢复 status=4，正常安排和跨账号引用需给出明确结果。
2. 幂等 request UID、并发版本条件、重复请求可查询结果；超时不应导致客户端盲目重放。
3. 恢复后的状态应明确（建议 following），返回最新完整安排投影与版本。恢复不应自动重启过期提醒、重复推送，亦不应把过期安排改成今天。
4. 删除时软删的快记关联、来源链路是否恢复，须明确。如果相关记录已删除或无权访问，安排可以恢复，但对应来源必须返回独立 unavailable 原因。
5. 是否存在清理期限、删除时间、可恢复截止时间等 owner 字段，请明确返回，不能让客户端把 update_at 当作 deleted_at 或猜测30天。

## 缺口2：已删除安排的来源原文访问

当前 source/read、source/open 的安排状态校验仅接受1/2/3。已删除安排详情能够读取基础字段，但已有来源协议不能直接用于status=4。

请明确选择正式权限策略：

- 如果允许本人在已删除中查阅原文，请在后端按账号、安排与证据关联校验后允许status=4读取；独立返回原文已删除、安排已清理、无权访问、依据不匹配等原因。
- 如果仅允许恢复后查看，请提供 capability / reason，前端根据服务端事实展示“恢复后查看”，不要只靠前端判断状态后规避权限检查。
- source/open 与 source/read 必须共用相同的 owner 与证据关联校验；不能由前端上传原始记录ID、文本或另一账号引用来绕过。

## 联调验收

- 数万条安排场景，日期筛选需由服务端先过滤再分页；排序与总数来自同一筛选。不能忽略新字段后返回整页旧数据。
- 已删除页真实请求status=4，不能从普通安排列表过滤得出“空”；详情读取被恢复或再次删除时，须报告最新状态。
- 账号切换、来源删除/撤权、完成/删除并发、重复恢复、写入超时及提醒到期等路径均需覆盖。
- 接口完成后请回传正式路径、请求/响应样例、错误码、幂等与版本策略，以及部署环境；前端再接恢复与已删除原文访问。
