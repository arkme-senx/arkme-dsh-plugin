# 长文转发副本显示类型：合同补充核对

日期：2026-10-26。此次发布前全量回归发现，需要补充确认转发条目的正式写入合同。

## 已确认的插件证据

- 插件 `src/services/chat-service.ts` 的 `forwardPayloadItem()` 新增了转发条目的 `display_kind`，用于保留原文的长文显示类型。
- 当前仓库的严格 Record 转发写入合同固定在 `tests/fixtures/record-forward-input.ts`。`content_payload.forward_records.items[]` 允许 `template_kind`、`text_format`、`text` 等字段，但没有 `display_kind`。
- 向发给自己、默认分类和主题转发普通消息的三项测试均因此抛出 `json: unknown field "display_kind"`。字段被无条件附加，所以影响不限于长文。
- 这份文档描述的是本地严格合同回归结果，不是一次实际生产转发的错误回执；本次没有为测试创建额外云端消息。不能把测试结果冒充为生产接口当前必然返回 HTTP 400 的证据。

## 请后端确认或补齐

请确认以下现有 Record 写入入口的正式 DTO：

- `/api/v1/records/create`
- `/api/v1/topics/records/create`

重点是 `content_payload.forward_records.items[]`，不是顶层原始 Record 的 `display_kind`。原始 Record 已能返回显示类型，不等于嵌套转发条目的写入也支持同名字段。

如果当前已支持，请回传写入 DTO、测试/生产部署版本及脱敏的真实写入与读取响应，插件据此更新严格合同和集成测试；不能仅放宽本地测试。

如果尚不支持，建议增加保存与读取原文显示类型的正式字段。需要明确：

1. 原文与只读转发副本各自的稳定身份、显示类型、正文格式，以及副本是否保存发布时快照。
2. 含图片的 Markdown 长文仍保留长文身份，不将附件条目或普通消息误判成长文。
3. 老客户端未带该字段时的默认语义；新客户端发送新字段遇到旧服务时应如何协商或降级。
4. 创建、历史分页、复制链接快照、转发详情等链路是否都能读回相同的显示类型。
5. 原文权限与转发快照权限分开裁决，不因保存显示类型而增加读取原文或私人元数据的权限。

## 插件当前发布处理方案

拟先遵循已知严格写入合同移除该条目字段，继续保留完整正文、Markdown 格式和已有来源信息；此项代码修复尚待本轮用户确认。原始长文的编辑、复制链接、导出和已有长文详情不依赖这项嵌套字段扩展。

这并不承诺旧服务能保留新增的长文副本专用显示方式。取得正式合同后，再接上显示类型保存与读取；不得把 `template_kind` 改写成并非原文的值来伪造类型，也不得通过放宽测试掩盖写入差异。
