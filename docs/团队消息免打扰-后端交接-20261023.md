# 团队消息免打扰：后端交接

日期：2026-10-23。范围：当前用户对一条团队外部对话的通知偏好。

## 产品行为

用户在团队消息对话右上角「…」打开或关闭「消息免打扰」。只影响操作者本人对当前对话的提醒，不改变其他成员的设置，也不暂停团队接收外部消息。消息与原始未读数继续保留，读游标不因免打扰改变。设置需跨重启、跨设备保持。

私聊已复用 Chat 的 `/api/v1/chats/policy/get`、`/api/v1/chats/policy/update`，写入仅提交 `mute_state` 和 `notify_state` 字段意图，保留置顶、隐私等其他设置。团队对话不能把 `conversation_uid` 当作 Chat 的 `chat_session_uid` 直接调用该接口。

## 当前插件证据与缺口

- `src/team-app-contract.ts`：`TeamConversation` 只有原始 `unread`、读游标及会话状态；没有当前查看者的免打扰状态、有效通知权限和策略版本。`TeamAppOperation` 未接入通知策略查询/修改。
- `src/services/team-app-service.ts`：目前接入 `/api/v1/team/conversations/*` 系列接口，包括 `home-visibility`、`read/advance` 和 `block`，未接入通知策略。屏蔽用户和关闭通道均不能代替个人免打扰。
- `src/client/team-attention-store.ts`：`conversations/attention` 目前映射为 `external`、`team`、`applications` 三个布尔值。
- `src/client/TeamMessagingPanel.tsx` 的 `TeamMessagingMount` 根据上述汇总信号发送系统通知，不知道具体哪个会话触发。仅在前端增加本地开关无法可靠过滤当前对话，可能误屏蔽其他团队对话。

以上是当前插件接入协议的已确认缺口，不代表已经核验所有后端部署。若后端已有对应能力，请提供正式路由、字段、事件和部署环境，前端可直接适配。

## 建议接口与同步契约（待后端确认，不是已存在路由）

1. 按 `conversation_uid + side` 查询当前登录人的通知策略，响应包含 `muted`、`notification_allowed`、单调递增 `policy_version`。
2. 按同一目标设置明确布尔意图 `muted`，相同意图重复提交幂等；只修改本次目标字段。返回服务端生效值和版本。是否启用乐观并发由后端统一约定；冲突必须返回可重新读取的当前状态，不能覆盖其他字段。
3. 策略归属由服务端认证决定，不接受客户端指定任意用户。团队成员须仍有权限访问目标会话；外部访客只能修改自己的可访问会话。团队成员甲的设置不能影响乙。
4. 会话列表、上下文及增量事件返回当前查看者的策略与版本。策略变更应通知该用户的其他在线设备，不能向其他成员泄露该偏好。旧响应或旧事件不能覆盖新状态。
5. 未读分清原始未读与提醒口径：原始 `unread` 保留，注意力/通知汇总按当前用户策略过滤。静音会话显示免打扰图标；不改变既有读游标。
6. `conversations/attention` 应返回已经按当前用户策略过滤的消息提醒，并保留加入申请的独立语义。若采用会话级通知事件，应携带可定位会话身份、事件版本和去重标识。移动端推送、桌面端提醒及聚合提示须使用相同策略，不能只靠客户端隐藏系统弹窗。
7. 解除免打扰后保留原始未读；是否补发旧未读提醒须明确，建议仅恢复后续新消息提醒，不集中弹出历史通知。
8. 接口未支持、权限失效、已离开团队与临时失败应可区分；可通过能力字段或明确错误码识别。UI 不把失败当作「已关闭」。

## 验收

- 成员甲静音访客 A 后，甲不再收到 A 的新消息提醒；甲仍能收到访客 B 的提醒，成员乙仍能正常收到 A 的提醒。
- 静音不减少原始未读，不推进读游标，不阻止外部用户发送消息。
- 混合存在静音和非静音对话时，汇总提示正确；加入申请提醒保持独立。
- 重启、换设备、分页读取和旧事件晚到后状态仍一致；无权用户不能修改策略。
- 保存超时后重新查询真实状态；不盲目重复提交，不把未知结果展示为成功。

## 本轮前端范围

- 本轮不改后端服务，不自动发送本文或合并发布。
