# 桌面导出：日期范围与可靠增量交接

日期：2026-11-03。需求：现有桌面数据导出每次全量，增加按日期导出，以及自动选择新增部分的增量导出。

## 一、当前交付与边界

- 前端已准备「全部 / 按日期 / 增量」入口，开始/结束日期、最近7天/本月/上月、附件选择、校验及未接通状态。
- 本轮没有修改 Record 后端，也没有给旧接口发送臆测的日期或游标字段。只有「全部且包含附件」继续执行现有导出；其他选择明确显示「后端接口开发中，开发完成后此功能完整可用。」，不创建任务、不消耗额度。
- 日期和增量模式不展示全量计数冒充本次范围数量。旧 latest_at 只标为「最近生成备份」，不当作已保存基线。按环境/账号隔离，切换账号重置导出视图。
- 这不是日期/增量端到端已上线。需 Record owner 确认正式合同、部署，再完成前端适配及真实桌面保存验收。

## 三、产品语义

### 1. 日期范围

- 按记录显示日期（现有 send_at 语义）选择，起止日期均包含；底层用 `[start, endExclusive)`，结束是所选结束日期的下一个本地日零点。
- 时区为本次选择明确绑定的 IANA 时区，不能简单用 UTC 截日或加24小时处理夏令时。
- 「最近7天」包含今天共7个日历日；「本月」月初至今天；「上月」完整上一个月。
- 无效日期、开始晚于结束在本地和服务端均拒绝。范围为零条时明确返回零，不启动扣额度任务。
- 日期导出不更新整份备份的增量基线；仅导出某一月不能让其他日期被标为已备份。

### 2. 增量

- 用户文案简写「增量」，语义为新增及更新。新增旧日期/历史导入的记录也必须出现；不能用 send_at > 上次导出时间实现。
- 首次无可验证的完整基线时先做全量。存量 latest_at 没有已保存证据，不能直接升级成增量基线。
- 记录修改、附件新增/替换/移除、影响导出正文的异步转写等，应进入同一个可查询变更事实。需确认这些变更是否都会推进 record version/update_at；不满足时由 owner 补稳定 export revision/change log。
- 删除/撤回/隐私锁定或恢复的变化需有定义：增量清单可用稳定ID及版本记录删除/排除状态，不输出已无权读取的正文或附件。输出历史备份不能被远程删除；需明确这是本次清单的状态。
- 每次独立ZIP标注范围和序号；增量包不是完整备份，界面提示与此前备份一并保留。包内加入机器可读清单，稳定记录ID、版本、基线ID和本次上界用于后续合并。
- 第一版对本次新增/更新记录附上其完整所需附件，暂不跨包省略附件，避免丢失此前包后本次不可读。跨包去重后续仅允许在可核验的同一备份链内使用。

### 3. 成功与重试

- 现有 finish(success=true) 只证明ZIP生成，不证明下载保存。保留旧语义，不因新增机制破坏旧客户端额度结算。
- 单独记录「生成成功」和「保存成功」。桌面需可信的原生下载完成/本地写入完成回执；不能用点击下载、HTTP开始、ZIP生成、或浏览器 beforeunload 当保存成功。
- 插件Host与安装客户端之间目前未核实到可供此功能消费的保存回执合同。客户端负责人需确认是否已有桥接能力；没有则补最小的按制品ID关联的完成/取消/失败回执，或由Host负责授权的流式保存。
- 普通Web若无法可靠判断最终落盘，必须明确使用用户「已保存」确认，不伪装自动确认。产品一期桌面验收不以Web下载按钮点击替代。
- 只有保存成功后推进备份链；失败、取消、仅生成、文件过期未保存、完成回执不确定均不推进。任务本身可重取状态，避免重试导致多次扣额度。
- 本次快照上界在任务开始时固定。任务进行中产生的新变更留给下一次，不能把 finish_at 当上界。

### 4. 设备和账号

- 基线按账号/环境/备份链隔离；各设备默认独立备份链。A电脑保存不能让B电脑默认跳过尚未拥有的历史包。
- 云端可保存链状态用于重装恢复；切换设备复用链必须确认已有基线文件，不因同账号自动套用另一个设备的进度。
- 并发导出对同一链使用expected checkpoint/version CAS；重复确认幂等，冲突刷新状态，禁止较旧任务覆盖较新基线。

## 四、后端合同建议（待 owner 确认，不是已实现API）

优先扩展现有会话owner；不要让前端读取全部历史后伪装成范围导出。字段名和最终路由由后端确定，下列为语义要求。

| 阶段 | 需要补充 |
| --- | --- |
| 能力探测 | 明确版本化支持日期、增量、附件开关及保存确认；未知能力按不支持，旧请求仍是全量 |
| preflight | 选择范围、时区、是否含附件、链ID/已确认游标；返回该范围记录/新增/更新/附件数、额度裁决、基线状态；结果绑定选择指纹 |
| start | 同一选择；幂等键；冻结范围/快照上界，返回会话ID及实际计数；不接受前端任意伪造的用户ID或无权链ID |
| records/page | 使用会话内范围与快照；不透明分页游标；稳定ID/版本；新增和更新不能混用 send_at 边界；保证同毫秒多条记录无遗漏 |
| files/batch-sign | 仅本会话已授权范围内的引用；重新校验账号、删除与隐私状态；有文件数/字节/过期上限 |
| finish | 保持旧ZIP生成/额度语义；新增任务可查，失败幂等、不会重复扣费 |
| saved acknowledgement | 服务端签发的制品/会话关联、链ID、expected checkpoint、回执幂等键；只有可信保存完成才能推进至本次已冻结上界 |
| status/latest | 区分生成/保存、全部/日期/增量、链状态；不复用单一 latest_at 表达所有事实 |

性能：按 user_id + send_at/稳定UID 做日期查询；按 owner 的变更序列或 update_at+稳定UID 做增量查询并建对应索引。预检、分页和签名共用同一范围解析与权限过滤。避免每次输入日期都扫全库；前端最终通过显式确认范围/短防抖取消请求更新统计。响应携带选择指纹，旧请求完成不能覆盖当前选择。

快照：请明确一致性实现。若分页期间可读到新版本，就需要可重复的物化清单/版本快照或其他可证明的变更上界协议；仅保存时间戳、不约束查询，不构成快照。权限收缩要及时生效，必要时使当前任务显式失败并重算，不能为凑足count导出无权内容。

额度：全量/日期/增量沿用何种会员频次由 owner 确认；前端不得绕过已有导出额度限制。零变更、重下载现有有效制品不创建新的计费导出。

## 五、前端接入点

1. `record-export-selection.ts` 目前只管理UI选择和校验，尚未转成网络合同。
2. 后端确认后扩 `data-management.ts`、SDK、Host参数校验、DataManagementService 预检与 RecordExportService 执行；以确认的能力开启真实导出。
3. 统计请求随选择变更，取消旧请求并验证账号+选择指纹；保留原有取消、签名隔离、流式ZIP和大小上限。
4. 对齐桌面保存回执后才实现自动默认增量、设备稳定目录持久化及云端链状态；不得先在localStorage保存 latest_at 冒充完成。
5. 并发/账号切换、未保存、回执不确定等状态都必须在UI真实呈现。

## 六、验收清单

- 日期：起止同日、月末/跨年/闰年/夏令时、无效范围、零记录；计数与包内清单一致，范围外附件不请求签名。
- 增量：同毫秒多记录、补录旧send_at、修改已导出记录、附件变化、删除/恢复/隐私权限收缩；每种变更在下一包正确出现。
- 快照：导出中继续写入/修改，结果不重不漏；新变更归下一包；分页重试可重复。
- 可靠性：下载取消、磁盘满、断网、退出、ZIP过期、回执丢失/重复、并发保存、账号切换，均无错误推进或重复扣额度。
- 安全：跨账号/跨环境/跨链游标、伪造保存确认、越权签名、异常范围和资源放大均拒绝；分页和索引有实际隔离数据库回归与性能对比。
- 兼容：旧客户端全量/主题请求仍通过，滚动部署中缺失新能力只明确阻断新模式，绝不降级为全量。
- 真实桌面：至少一次全量保存建立基线、制造隔离账号新增/修改后一次增量保存、失败重试一次；验证磁盘ZIP内容和链进度。真实用户生产账号只做只读界面验收，不为测试消耗其额度。

建议先交付日期过滤和匹配计数，再交付变更游标/备份链及保存确认。前端入口在同一页，无需后续重新讨论功能位置。
