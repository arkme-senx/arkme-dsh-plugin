# 云端历史缓存刷新与性能验证

## 行为

- 云端会话每次打开前仍验证账号归属与服务端历史修订；持续打开的订阅沿用原有 20 秒检查周期和 64 个流的上限。
- 历史正文修订包含历史代次、存储类型与进度。标题、源更新时间不参与正文失效判断；标题及创建时间作为单独显示修订。
- 缓存命中时直接返回本地页，不重写快照与事件。LRU 访问时间仍有小型元数据更新，不宣称整个 SQLite 完全无写入。
- 标题变化仅更新快照，不下载正文、不删除旧页。仅源更新时间变化不会重新发布历史快照。
- 同一历史代次的进度推进保留已缓存旧页；下载到的相同事件跳过 SQL 更新，只持久化新增或不同的内容。网络仍按既有五轮分页读取，未把它改成全量下载，也未宣称只下载新增事件。
- 迁移/历史代次变化、序号回退、显式 reset 继续原子清理残留。服务端提供有效修订时，无修订以及旧版混合修订的缓存先完成一次验证和重建；旧服务端不提供修订时仍不能信任持久缓存。
- 权限、下载前后版本校验、取消、分页连续性、256 会话与 128 MiB 缓存上限保持原 owner。

## 可复现的 Host/SQLite 对比

```sh
node --expose-gc scripts/profile-dsh-cloud-cache.mjs --baseline d1015458 --output /tmp/cache-before.json
node --expose-gc scripts/profile-dsh-cloud-cache.mjs --output /tmp/cache-after.json
```

同机顺序运行两个独立进程。基线通过 Git 只读加载指定提交的传输和缓存模块，不修改工作区。负载为 50000 个原始事件、500 轮对话，每个事件含 512 字节文本；1/4/8 个并发消费者代表多个窗口共用一个 Host。暖打开、无变化轮询、改名及仅更新时间变化各测 20 轮；另外覆盖冷打开、追加一轮、迁移换代和关闭清理。

记录元数据/历史请求数、传输字节、真实 SQLite INSERT/UPDATE/DELETE 次数、耗时样本和堆变化。两版本使用相同的 SQL 计数触发器、2 ms 模拟请求延迟、事件数据和校验代价。迁移换代前重新填充相同数量的缓存事件，避免把两个缓存规模不同的场景比较为性能改善。

这项对比测量 Host/SQLite 路径，不是公网延迟或页面 FPS。原生格式校验在该可控负载中替换为相同的空校验函数；真实官方 DSH 兼容和真实 Electron 窗口验收须另外报告。机器竞争负载会影响耗时，不能仅用单次 p95 声称所有设备无性能回归。

2026-10-13 在 macOS arm64 / Node 25.5.0 上，以 `d1015458` 为基线顺序重复三轮，1/4/8 消费者均完成。下表为 8 消费者 × 20 轮的计数，三次结果一致：

| 场景与指标 | 修改前 | 修改后 |
| --- | ---: | ---: |
| 暖打开：正文 SQL UPDATE | 80000 | 0 |
| 暖打开：快照写入 | 160 | 0 |
| 改名：历史分页请求 | 800 | 0 |
| 改名：历史响应字节 | 47858400 | 0 |
| 改名：快照写入 | 160 | 20 |
| 改名后保留的缓存事件 | 500 | 50000 |
| 仅更新时间：历史请求 / 快照写入 | 800 / 160 | 0 / 0 |

同代追加 100 条后的三次结果均为只插入 100 条、更新和删除均为 0，全部 50100 条缓存与源数据逐条规范化摘要一致。换代仍删除 50100 条旧缓存并保存正确的最近五轮 500 条，关闭后的订阅数均为 0；正文的其余历史仍由原分页接口读取。

暖打开每轮 160 个耗时样本，三个 p95 分别为基线 403.35 / 876.96 / 697.87 ms、修改后 83.94 / 254.43 / 83.78 ms。期间开发机有明显 CPU/内存竞争；这些是该机器上的观测值，不是跨机器 SLO。冷读、追加和换代仍有网络与 SQLite 成本，未宣称所有路径或页面 FPS 都有同等改善。

## 确定性门禁

`tests/dsh-cloud-cache-refresh.test.ts` 使用真实 SQLite 和事件写入计数，验证缓存命中不重写、四窗口改名只更新一次小型快照、反复轮询不写正文、追加保留旧页、迁移清理、旧缓存升级、序号回退以及缓存不绕过账号归属校验。

现有 cloud/native/cache 测试继续验证版本切换期间拒绝提交、取消不写半成品、无界订阅保护、页连续性与失败回滚。大历史对比逐条规范化摘要验证改名和追加后的全部缓存内容，迁移后校验保留页与服务端内容一致，并检查全部流已释放。

业务入口未增加：Tools、公开 SDK、UI 继续共用原账号会话 owner；本次没有新增路由、授权或写入生产数据的入口。优化仅影响插件侧可重建历史缓存。

## 官方安装与真实多窗口复核

同日将最终运行时代码打包为 tgz，经官方 DSH CLI 安装到全新 Profile，使用未修改的 DSH 0.1.5-rc.2、Electron 43.2.0 和独立客户端实例连接测试服。四个真实 Electron 页面共用同一个 Host，三个辅助窗口通过 Electron 的公共 BrowserWindow API 创建；此场景覆盖并发页面消费，不代表客户端正式多窗口入口或多个 Host 进程验收。

在数据副本中放入旧标题、无修订快照和超出服务端游标的残留事件，真实页面首次读取后从 14 条旧缓存恢复为 seq=0..12 的 13 条原始记录，逐条一致。之后四窗口共 80 次暖打开，以及每窗口连续 3 次按原 20 秒等待周期执行的轮询，正文 INSERT/UPDATE/DELETE 均为 0，全部返回内容保持一致。仍有权限检查、元数据请求和 LRU 元数据写入。

首次轮询驱动在每轮设置跨窗口屏障，使较快窗口等待最慢窗口，出现既有 45 秒闲置租约到期。保留失败记录后，改为每窗口独立连续拉取，12 次检查全部完成；业务租约、轮询周期和错误断言没有调整。真实测试服延迟不受控，这组结果不作为响应时间 before/after 对比。

测试服只读复核确认主记录与唯一会话数相等，原始事件和轮次记录无缺失、无改写，旧来源地址与保留地址的全量分页摘要一致。本轮迁移仅执行默认 dry-run，没有生产操作。六组既有 v0 日志仍存在当前 DSH 原生格式兼容限制，原数据和原接口可读；本轮没有伪造格式版本或扩大历史修复范围。
