## 1. 先看结论与实施顺序

现有团队通道已经支持外部用户联系团队。本轮补的是团队主动联系用户，以及团队身份、内部群和成员管理。**前端入口、真实数据选人、预览、权限检查与待接入提示已完成；新增写入能力仍未接通，不能把前端预览当作后端已上线。** 当前统一提示为「后端接口开发中，开发完成后此功能完整可用。」

请先确认线上是否已有可复用能力，再提供确切协议；下文建议路径不是已存在接口。不要只把插件的 `backend_pending` 改为 `ready`，还需接入真实写入、返回投影、权限与恢复逻辑。

| 顺序 | 后端交付包 | 完成标准 |
| --- | --- | --- |
| P0 | 双向团队私信 | 团队成员主动指定外部用户，复用唯一团队会话；首条消息后双方与同事真实同步 |
| P0 可并行 | 批量添加团队成员 | 管理者选多人，真实直接加入或邀请；逐人结果、幂等与成员变化事件完整 |
| P1 | 个人代表团队发言＋公开名片联系 | 不要求团队先入群；消息显示实际操作者和团队；外部用户可联系团队 |
| P2 | 团队内部群 | 创建或关联，服务端随团队名单自动增减成员，历史范围与撤权正确 |
| P3 | 团队正式加入普通群 | 团队独立主体入群，授权同事代理查看和回复，统一混合会话目录 |
| P4 | 群内互动归集 | @团队、回复团队的群消息以原文引用呈现在对应团队私信，权限和去重完整 |

### 已确认的产品规则，避免沿用旧理解

1. **个人已经在群内，且真实创建或加入团队，即可代表团队发言；不要求团队先入群，也不额外要求团队管理员角色。** 发送仍需符合正常群权限。代表发言不会自动给同事群访问权。
2. 团队成员资格、个人群成员资格、团队群成员资格、团队代理访问权限分别校验，不能相互替代。仅申请中、退出或被移除不算有效成员。
3. 与团队名单绑定的内部群按本人发言，不显示身份选择器；不能因群名或成员恰好都是同事而推断绑定。
4. 团队私信、团队参与的群、团队内部群在同一列表混排，置顶优先，其余按最新消息时间排序；不增加用户／群聊 tab。
5. 团队身份是「本人代表团队」，主头像仍是本人，另加团队角标。所有有权读消息的人都能辨认具体回复者与团队。
6. 个人私聊历史、私人备注、私密快记不会自动共享。未来「发给自己」选择工作／团队身份也仍是本人私密内容。
7. 团队名片的「我也要创建团队」是底部低强调文字入口，复用现有创建团队接口，不需另做一套创建接口。

## 2. 当前前端及插件 Host 边界

以下 `team.app.*` 是插件内部操作，**不是云端 HTTP 路由**。请求都绑定当前账号；不透明引用只能由各自签发服务校验、解封，不能用名称、备注或自填 ID 替代授权。

| 场景／操作 | 当前可验收内容 | 仍需接入 |
| --- | --- | --- |
| `team.app.outbound.open` | 私聊／群聊头像卡、联系人资料「以团队联系」；团队目录「联系用户」；真实团队、联系人分页及即我号／手机号精确查找 | 目标引用真实解析与访问校验、主动打开真实团队会话 |
| `team.app.member-candidates` | 管理者读取联系人、最近私聊、展开群聊选人；备注优先、头像、跨来源去重、完整成员状态、分页 | 已有读取已接通；不用新增复制的联系人系统 |
| `team.app.members.add` | 多选 1–50 人、已选头像、已加入禁选、保留失败选择；提交时重新校验账号／权限／引用／成员 | 真实批量加入或邀请、逐人结果与状态恢复 |
| `team.app.group.context` | 校验群引用，读取 list-mine 的真实团队，按需刷新；返回 pending／绑定 unknown | 真实群绑定类型、个人与代理资格、权限版本 |
| `team.app.group.join` | 添加群成员中的团队分类、选真实团队和检查；pending | 双方鉴权、申请／加入、可见起点与代理授权 |
| `team.app.group.directory` | 保留 Host 待接入边界；前端不再独立请求群分类页 | 统一团队混合列表，不以个人群填充假团队群 |
| `team.app.internal-group.prepare` | 团队功能「团队内部群」新建；群管理「关联为团队内部群」；真实团队与表单、pending | 预览、确认、状态查询、服务端绑定及名单同步 |
| `team.app.public-card` | 真实公开资料投影，介绍与低强调创建入口；有现成通道引用时可导航 | 外部查看者的公开通道定位、简介与真实联系状态 |

群身份按钮现在是本人头像＋「我」。点击团队候选进入本人＋团队预览，提示尚未切换、仍按个人发送；没有伪造团队消息。真实身份发送、独立草稿及全端消息徽标需要 P1 联调。内部群与团队入群当前也不会创建群或更改任何真实成员。

团队成员添加抽屉宽 380px／最多 92vw；联系人、最近对话、群内真人共同选人，不包含 Bot 或团队账号。姓名相同不同用户不合并；同一用户跨来源只提交一次。当前团队完整成员读取失败不当作「未加入」。

主要代码位置：`src/services/team-app-service.ts`、`team-outbound-contract.ts`、`team-group-contract.ts`，以及 `src/client/TeamOutboundDialog.tsx`、团队选人／内部群／公开名片组件和联系人团队详情。原五份分项交接仍保留在仓库 docs 中，本文整合其最终规则。

## 3. P0：双向团队私信

### 3.1 入口与权限

操作者在群里看到反馈后，可选该用户「以团队联系」，也可从联系人或团队目录发起。只选一个团队时默认选中，多个团队明确选择；界面说明有权限的同事共同查看回复，个人历史不共享。本人不出现此操作。

团队列表需返回 `can_start_external_conversation` 与拒绝原因，真实发起权限由服务端决定，不能只依前端角色判断。校验当前账号、有效团队成员、通道状态、目标存在、消息接收／拉黑／限流规则。第一阶段目标为团队外已注册个人；本人、团队主体和当前团队内部成员不作为外部客户。

现有 `/api/v1/team/conversations/open` 仅接受 `public_ref`，用于外部用户从团队入口打开；不能用它冒充主动指定用户。

### 3.2 请求及 Host 对接

插件请求：

```text
team.app.outbound.open
  expectedAccountKey, teamRef, requestUid
  recipient:
    chat-member       + sourceRef + memberRef
    directory-contact + contactRef
    contact-lookup    + contactRef
→ backend_pending
→ ready + conversation: TeamConversation（真实上游接入后）
```

当前 pending 实现仅检查目标参数形状，尚未解析目标、执行目标写入。接入前 Host 必须分别调用原签发服务解析三类目标，验证操作者能访问相关群／联系人／查找结果；不把三类引用互换。大整数 ID 保持字符串／现有 owner codec，不转 JS Number。

建议新增 `POST /api/v1/team/conversations/open-by-member`，或明确扩展已有接口：`team_id, external_user_id, request_uid`；实际操作者由服务端从登录态取得。

服务端对 `(team_id, external_user_id)` 保证唯一。外部先发、内部先发、多个同事同时发都复用同一逻辑会话；隐藏或归档后再联系不创建副本。`request_uid` 绑定操作者、团队、目标；同键不同参数冲突，超时可查原结果。

Host ready 投影沿用现有 `ref/key/side:team/channel/visitor/序列/未读`，核对返回团队与所选团队相符。引用可轮换，不按引用密文判断是否同一团队。进程重启后需可恢复未知结果，不能只依赖内存 requestUid。

### 3.3 打开、发送与同步

仅打开窗口不发送、不通知、不增加未读，不在外部收件箱制造空会话；首条消息成功后再激活并发布目录事件。第一条消息复用现有团队消息、附件、幂等发送队列及已读路径，不另建聊天系统。

团队端看外部用户；外部端看团队及真实成员署名。消息持久化代表团队与实际操作者。首条消息后同步双方及有权限同事的列表、预览、最后活动、未读；内部每人已读与外部已读分别记录，断线重连不能重复提醒。

每次读取和真正发送时重新鉴权；退出、撤权、通道关闭、拉黑等返回真实状态并保留未发送草稿。建议错误码：`not_team_member / outreach_forbidden / channel_disabled / recipient_unavailable / recipient_is_self / recipient_is_team_member / recipient_blocked / rate_limited / request_conflict`。

主窗口入口已准备。固定绑定原会话的独立聊天窗口暂不显示新入口；后续需客户端支持带团队目标激活主窗口，不能悄悄改变固定窗口的会话。

## 4. P0 并行：批量添加团队成员

当前联系人、最近私聊和群成员读取均复用已有服务；Host 将候选密封为绑定账号、团队、用户的 `candidateRef`，有效期一小时。所有者／管理员显示添加入口；当前提交仍只返回 pending，不发邀请、不添加成员。

```text
team.app.member-candidates
  expectedAccountKey, teamRef, source: contacts | conversations | group
  optional sourceRef, cursor
→ items, groups, hasMore, nextCursor, optional coverage

team.app.members.add
  expectedAccountKey, teamRef, candidateRefs（1–50、不可重复）, requestUid
→ backend_pending（当前）
```

建议云端批量命令 `team/members/add`：`team_id, user_ids, role:member, request_uid`。请确认是否已有可用接口；现有群聊 `chats/members/add` 不能用于团队。

必须提供：

- 认证操作者和实时 owner/admin 或明确 capability；`can_add_members`、批量上限、人数配额和拒绝原因。选普通成员不授予管理权。
- 校验用户存在、接收／加入条件、团队状态、重复与已加入；同请求幂等，同键不同集合冲突；网络未知结果可查询。
- 逐人返回 `added / already_member / invitation_pending / rejected(reason)`，以及 `member_count / membership_revision / request_uid`。成功部分更新并禁选，失败部分保留供重试。
- 明确哪些场景可直接加入、哪些必须受邀者确认。`invitation_pending` 只能显示邀请已发送，不计为加入成功。
- 成员变化事件和通知说明团队与发起者；其他设备刷新真实名单、人数和权限。私人备注仅供当前查看者，不外传。
- 若内部群已绑定，后端统一驱动名单同步并返回进度，前端不能逐个调用个人群接口模拟。未绑定普通群不受影响。

## 5. P1：个人代表团队发言与公开名片

### 5.1 权限和身份模型

| 当前情况 | 发言身份 | 同事可见范围 |
| --- | --- | --- |
| 本人在普通群，无有效团队 | 本人，不显示选择器 | 无新增共享 |
| 本人在普通群，属于团队，团队未入群 | 本人／代表所属团队 | 同事不会因此获得群访问权 |
| 个人和团队均已入群 | 本人／代表团队 | 团队代理访问仍按授权和加入起点 |
| 本人未个人入群，只有获授权的团队代理访问 | 固定代表团队；多个可用团队可选 | 仅团队被授权范围 |
| 团队名单绑定的内部群 | 本人，无身份切换 | 内部群规则 |

上下文需分别返回 `membership_policy`、个人群资格、真实团队成员状态／版本、是否可以代表、团队是否正式入群、代理访问资格／版本、拒绝原因。不得以 `team_group_membership` 存在作为个人代表发言的条件。

发送建议增加：

```text
represented_principal_kind: personal | team
represented_team_id
actual_actor_user_id                 服务端从认证态确定
actor_team_membership_revision
group_access_kind: personal_membership | team_delegation
team_group_membership_uid/revision   仅代理访问要求
origin_group_uid, origin_message_uid, message_revision
```

个人路径检查本人群资格、真实团队成员及禁言／发送规则；代理路径额外检查团队已入群、代理授权与可见范围。`request_uid` 固定群、操作者、身份、正文、附件、引用；参数变化返回冲突，未知结果可查询，不把团队发送降级成个人发送。

消息所有读取路径返回实际操作者与代表团队。主头像为操作者，叠团队角标；名称为查看者备注优先的人名＋团队标识。点击个人头像开个人卡，点团队标识开公开团队卡。同事消息使用他人底色。历史身份保留当时事实，退出团队不改写旧消息归属，当前团队资料可独立更新。

编辑、撤回、删除、详情、延展、转发、分享、导出、搜索、附件均保留正确身份与权限；不能只接主发送按钮。发言身份与原文权限跨设备一致。

### 5.2 前端接入要求

默认本人；候选「我／个人身份」「我 · 团队名／代表团队发言」，本人头像始终保留。收起时短按钮，完整团队名在悬浮及原有发消息提示展示。确实只有一个身份时固定，不显示无意义选择器。

按账号、群、入口上下文记住选择，个人／团队各自保存文字、附件、引用、上传及输入统计。切换不挪用个人草稿。发送冻结身份；权限失效保留草稿并拒绝，回复／@／刷新不自动切身份。快捷键、表情、语音、长文和离线队列同样遵守。

### 5.3 公开资料与联系定位

已有 `team.app.public-card` 请求 `expectedAccountKey,jotmoId`，仅投影公开信息。所属团队可从 list-mine＋成员专用 message-channel/get 取得既有 publicRef；外部用户目前 discovery/search 可取得基本资料，缺公开联系定位，不能越权调用成员配置接口。

请提供有合法入口的外部用户可读的团队稳定标识、名称、头像、公开简介（可空）、联系状态及稳定 `public_ref`／签名导航引用；区分 `available / disabled / unavailable` 与技术未接入。现有 public resolve 要先有 public_ref，无法由即我号猜出，不能替代此能力。

只返回公开投影，不泄露名册、内部项目／配置或管理凭证；消息团队标识由服务端确定，不信任正文自填标签。联系沿用登录、接收规则、拉黑和限流。点击联系复用团队与当前用户唯一通道；本人为成员时进入团队收件箱。看卡片不创建会话、不发消息，通道关闭／团队解散给真实状态。

名片已加团队协作介绍和底部灰色小字「我也要创建团队 ↗」。创建复用现有 `team.app.create.check/create`、表单及账号校验；取消返回名片、草稿保留。点击入口本身不创建、不自动加入当前团队、不预填他人名称、不自动开通通道或邀请。该部分不需要新增创建 API。

团队未正式入群时，代表消息仍是原群消息，回复通知实际发言人；不自动创建 @团队 群成员，不推送群历史给同事。外部用户主动从名片联系团队后，只共享该通道中明确发送的内容。

## 6. P2：团队内部群和成员自动同步

一个内部群明确绑定一个团队；一个团队可有多个内部群。新建和关联均要求团队 owner/admin；关联第一版还要求原群群主。具体权限最终由服务端 capability 决定。

现有 Host：`team.app.internal-group.prepare(expectedAccountKey,teamRef,requestUid,mode:create|link,name?,sourceRef?)`。create 名称去首尾空白后 1–120 字；link 必须 group_chat 引用。当前校验团队管理角色及引用类型，不证明群管理权、绑定状态或预览已通过，不写入。

云端闭环：

1. **预览**：新建返回当前真实人员／人数和历史策略；关联返回新增、移出、保留的个人及单独列出的 Bot，双方权限与绑定状态。
2. **确认**：短期 preview token 绑定账号、团队、群、团队名单版本、群版本、名称和历史策略；确认再次鉴权，变更返回 `preview_stale` 重新预览。不能静默踢掉旧群非同事。
3. **原子提交**：生成稳定群／绑定 ID、revision、成员同步进度；requestUid 幂等，同键不同参数冲突，未知结果可查询，不重复建群。
4. **持续同步**：服务端持久化名单事件、唯一事件 ID、单调版本、可靠队列重试和低频对账；与客户端是否在线无关。不让前端轮询后逐个增删群成员。

新群人类成员等于有效团队名单；旧群 Bot 单独预览、默认保留，之后按群权限管理，不能随人员同步误删。内部群的人类成员入口导向团队管理，不再独立手动加／移人。内部群管理角色跟随团队 owner/admin，旧群主离职不能残留权限。

新同事默认仅能读本次加入后的消息；关联时已有成员保持合法历史范围。开放更早历史须显式策略预览确认，不隐式扩大。退队立即停止在线读写、搜索／统计／导出、附件／分享原文访问；旧消息保留实际作者。重新加入是新版本、新起点，不复活旧权限。

绑定权威规则原子生效，即使投影队列尚未更新，授权也按当前团队名单判断，避免离职撤权延迟。缓存内容无法保证物理收回，但客户端停止展示／新请求并清授权缓存。

第一版不开放自行退出内部群、换绑或解绑；隐藏／免打扰不等于退出。团队解散后冻结／归档内部群，不能转成仍可读的普通群。内容保留策略由后端明确。

同一 canonical group uid 可从普通列表或团队列表打开，不复制群／消息，不重复未读／通知。

## 7. P3：团队正式入群、代理访问与混合目录

团队是 `principal_kind:user|bot|team` 中独立 team 主体，占一个群成员位置，不是批量把所有员工加群。入群同时满足群邀请／审批和团队入群权限；list-mine 只能证明成员资格，不证明有权邀请团队。

建议加入请求：group、team、requestUid、预期权限版本；返回 `joined / pending_approval / rejected / already_joined`、团队群成员引用、版本和可见起始 seq。加入后群系统通知明确获授权团队成员可查看参与。

默认仅可读团队本次加入之后的消息；未个人入群的获授权同事走团队代理上下文，不能调用个人入口绕过。退出／移除立即停止读写，重新加入产生新成员版本和起点；默认撤权后不开放历史在线查询，必要审计需另设权限。

提供代理上下文、时间线、发送／状态查询和权限变化事件；按各自引用 codec 解封，检查真实授权。团队群引用不能交给当前仅支持一对一的 `team.app.timeline` 等接口。

统一混合列表需返回：`conversation_kind:team_direct|team_group|team_internal`、稳定 key、合法导航引用、代表团队、头像／名称、最新消息及时间、未读、置顶和分页 cursor。置顶优先，消息时间降序，同时间稳定 key；资料修改、回执或分页时间不把旧会话顶前。

若后端暂分两个源分页，Host 维护双游标并合成有序结果，不能先加载所有私信再追加群。部分失败保留已有内容、说明受影响范围并重试；无权限剔除对应项，不伪装空列表。后台更新保留阅读位置。移除入口只隐藏、不退群。

个人入口与团队入口共用原消息事实；个人已读、团队内部各成员已读和外部已读语义明确，按原消息唯一键去重。成员离队、移出团队、入群审批、撤权事件使客户端重读上下文并撤销过期订阅、引用和授权缓存。

## 8. P4：群内互动归集

仅在团队正式入群且具备来源权限时，将显式 @团队、回复团队消息、团队对指定外部用户的群内回复，以原消息引用归集到 `(team,external_user)` 通道的来源群卡片。个人代表团队但团队未入群时不自动归集，不借此共享群上下文。

同一消息只存一份事实，不复制发送、不重复提醒或未读。来源卡片默认回复原群，输入前明确「回复到某群」；改为团队私信必须显式选择，不能把私信自动发回群。普通无关群消息和个人私聊不归集。

展开上下文、原文、复制链接、转发都重新鉴权；外部用户不能经通道读无权访问的群消息。编辑／撤回／删除反映同一版本，不留下绕过权限的完整副本。

## 9. 后端交付与联合验收

请按交付包返回：确切环境／路由、请求响应及字段类型、能力与角色矩阵、真实业务错误码、版本与事件、幂等／未知结果查询方式，以及成功和失败示例。已经存在的接口请指出复用方式，避免重复建设。

最少验收：

- 双向发起／多人并发／隐藏后恢复只存在一条团队私信；空打开无外部通知，首条消息后同事和外部设备同步；私人历史与备注不外泄。
- 选人跨来源去重、同名不合并；部分加入／邀请／拒绝真实反馈；配额、撤权、过期引用、超时和重复提交可恢复。
- 团队未入群，普通成员仍可代表发送；同事不因此读群；所有收件人与设备看同一操作者和团队；公开名片能联系正确通道。
- 团队身份切换与上传、引用、键盘发送、离线重试不串草稿或身份；失效不能静默改个人发送。
- 内部群新建／旧群关联的差异确认、预览过期、Bot 保留、新成员历史边界、离职立即撤权、乱序和服务重启恢复完整。
- 正式团队入群、审批／拒绝／退出／重新加入均真实；代理用户和个人入口不越权，原文／附件／搜索／导出遵守同一历史范围。
- 混合列表跨来源分页、最新排序、未读去重、失败重试与阅读位置稳定；群引用和私信目的地清楚。

当前验证覆盖前端交互、真实读取、Host 校验与 pending 边界、构建和相关自动化测试；没有通过测试操作真正添加成员或创建群。真实新增能力、跨设备同步和权限撤销需后端交付后用授权测试账号联合验收。
