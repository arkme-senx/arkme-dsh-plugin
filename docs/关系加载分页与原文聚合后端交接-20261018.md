# 关系加载分页与原文聚合：后端交接

核查时间：2026-10-18（CST）。本轮只修改插件适配层和前端，未修改或部署 relation 后端。

## 结论与当前边界

关系界面已可先显示人物概述，再补原始记录；本次补上按账号保存的阅读缓存、后台更新和失败保留。缓存只能改善再次查看，第一次打开未缓存人物仍需要等待记录接口。需要后端补真正分页，并定位记录查询约 3.3 秒的固定等待。

以下为同一生产测试账号的只读抽样，不代表全体用户的 P95，也不是数据库瓶颈的最终结论。本文不附个人原文、登录凭据或生产数据导出。

## 已确认的证据

| 请求 | 实际返回 / 耗时 |
| --- | --- |
| `GET /api/v1/relation/list?limit=1&offset=0` | 仍返回 7,156 个实体，响应正文约 1,777,000 字节，602 ms |
| 人物样本 A `POST /api/v1/entity/records/list`，limit 6 / 30 | 3,331 / 3,457 ms |
| 人物样本 B 同接口，limit 6 / 30 | 3,304 / 3,371 ms |
| 插件人物概述分区（两个样本） | 约 30 / 36 ms |
| 记录第一页的原始行 / 唯一来源数 | 样本 A 30 / 28；样本 B 30 / 27 |

减小记录 limit 并没有消除主要等待。同一来源的多个 mention 被逐行返回，是重复卡片的来源之一。新版插件合并同一来源并保留提及位置，旧版插件仍可能逐行显示。

代码核查基于 `jotmo-relation origin/master` 的 `3f37a98`：

- `gin/api/relation.go` 的 `relationListHandler` 只读取用户身份，不读取 limit/offset。
- `gin/compound/relation.go` 的 `GetRelationList` 获取全部实体、处理可见性及字段、排序后一起返回。
- `gin/compound/entity.go` 的 `GetEntityRecordsList`（约 2291 行）依次涉及实体归属校验、总数统计、entity_record 查询、core_record 正文和 import_record 查询，再按需加载导入身份/绑定等信息。
- `internal/core_record/repository.go` 的 `SelectCoreRecordsByUids`；`internal/import_record/models.go` 的 `SelectImportRecordsByUids` 是正文补全的两个排查点。

目前没有取得这些请求的分阶段生产 trace 或数据库 explain，不能直接断言是哪个索引或哪个查询导致 3.3 秒。

## 后端需要完成

### 1. 真正分页的关系列表

建议通过明确的新协议版本或能力声明升级，避免旧客户端把分页结果误当全部：

- 接受 limit、cursor、类型和搜索条件；服务器按范围查询，不再全量回传。
- 返回 items、has_more、next_cursor、snapshot/version；总数/类型计数允许独立或延后返回。
- 排序必须稳定，包含唯一 ID 作为同时间项的排序兜底；新增数据后续翻页不能漏行或重复。
- 名称、别名、联系人备注搜索仍要覆盖完整账号数据，不能只搜已加载的一页。
- 按用户和可见性校验查询、cursor 与缓存，切换账号不得复用。
- 日志记录请求条数、返回条数、字节数、各阶段耗时，不记录原文或令牌。

插件当前的 `explore.list.limit` **只是本地适配层恢复已加载窗口的数量**，不是后端已经支持分页。现有后端无能力声明时仍走兼容路径。

### 2. 相关记录接口的耗时分解

请在同一个 trace 中记录：实体校验、count、entity_record 查询、core_record 查询、import_record 查询、身份补全、序列化以及总耗时。先找到真正的慢阶段，再调整：

- 检查真实查询计划、扫描行数和排序是否命中索引，而非只看代码声明过索引。
- 精确 total 不应阻塞第一屏；必要时先取 `limit + 1` 判断 has_more，计数独立请求。
- 能安全并行的正文读取可并行；明确不是导入记录时，避免无意义的导入身份补全。
- 设置字段投影和响应大小限制；分页接口不要夹带整个人物的全量历史。
- 用户权限、删除状态和正文读取错误仍须明确处理，不能用空成功掩盖失败。

### 3. 按原始记录聚合，保留全部提及位置

建议记录分页单位是唯一原始记录，而非 mention 行：

```json
{
  "records": [{
    "source_identity": { "provider": "core_record", "record_uid": "opaque-id" },
    "content": "经权限校验后的原文",
    "mentions": [
      { "start_position": 12, "end_position": 14, "mention_text": "名字" },
      { "start_position": 25, "end_position": 27, "mention_text": "名字" }
    ]
  }],
  "has_more": true,
  "next_cursor": "opaque-cursor"
}
```

明确 `total` 是原始记录数还是提及次数，分别命名。不要仅凭同文去重，不同来源同样一句话仍是不同记录。来自不同 provider 的同名 UID 不应冲突；多来源映射同一原文需要可信的 canonical identity。

## 插件已处理的部分

- 列表、选中人物、详情分别缓存；刷新/重新进入先展示已有内容，再更新。
- 缓存按环境及账号隔离，登出/切换账号清理；采用有界存储和最长 6 小时有效期。
- 人物信息和记录分区独立读取；一个区域失败不丢弃另一区域已返回内容。
- 已读后续页面保持可见；第一页刷新失败后重试第一页，不错误地跳到下一页。
- 同一来源合并为一张卡片，显示提及处数并保留原文定位。
- 来源打开仍由服务端执行当前权限检查，缓存不是访问授权。

## 联调验收建议

建议目标（待后端确认，并非当前已经达到）：普通网络下首屏列表和首批原文 P95 < 1 秒；缓存命中先显示 < 100 ms。至少覆盖：

1. 数千/上万实体账号冷启动，前 50 条不等待全部实体传输。
2. 同一人物 6/30/100 条查询，trace 可以解释各阶段耗时。
3. 同一原文在同页、跨页有多处 mention：一张卡片，位置完整。
4. 不同原文文本相同：仍分别显示。
5. 新增记录时翻页稳定；删除/撤权后不能继续打开来源。
6. 后端失败、离线、刷新、重新进入、切账号后缓存状态正确。
7. 对照实际安装的插件版本验收，不能只依据代码合入或 npm 版本号判断已生效。
